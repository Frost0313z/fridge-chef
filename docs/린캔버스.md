## ① 고객군 (Customer Segments)

- **핵심 타겟**: 식비를 아끼려고 직접 해먹으려 하지만, 냉장고 재고 파악과 장보기의 번거로움 때문에
  자주 배달로 타협하는 **20~30대 1인 가구 자취생**.
- **얼리어답터**: 기획자 본인. 실제 타겟이자 첫 사용자다.
- **의도적으로 뺀 사용자**: 앱 기반 조작 자체에 진입장벽을 느끼는 연령대. 이 서비스는 요리할 때마다
  스마트폰을 켜서 조작하는 것을 전제로 하므로 타겟을 좁혔다.
- **왜 재방문하는가**: 하루 1~2끼마다 반복되는 수요라, 한 번 습관이 되면 매일 쓸 이유가 생긴다.
  "내 재료함"·"최근 추천 이력"은 이 반복을 전제로 재입력 마찰을 없애려고 넣은 기능이다.

## ② 문제 (Problem)

식비를 아끼고 싶다는 욕망은 이미 충분히 강한데, 세 개의 장벽에서 막혀 배달로 되돌아간다.

| # | 장벽 | 결과 |
|---|---|---|
| 1 | 냉장고에 뭐가 있는지 파악이 안 됨 | 뭘로 뭘 만들 수 있는지 모름 |
| 2 | 뭘 사야 할지 몰라 장보기 계획을 못 세움 | 감으로 사서 겹치거나 빠뜨림 |
| 3 | 온라인 주문은 다음날 도착 | 오늘 먹을 끼니는 해결이 안 됨 → "일단 오늘은 시켜먹자" |

**심층 진단** — 표층 3장벽 아래 세 겹이 더 있다.

| 층위 | 진단 |
|---|---|
| 심층 1 | 서비스가 "산 것"(장보기)은 추적하는데 "먹은 것"(요리 소비)은 추적하지 않는 구조적 비대칭 — 재고 데이터가 시간이 갈수록 실제와 어긋난다 |
| 심층 2 | 문제는 **의지 부족이 아니라 마찰**이다 — 욕망은 강한데 행동으로 안 이어지는 간극 |
| 심층 3 | 고정 스케줄 설계가 불규칙한 자취생 식사 패턴과 안 맞아, 계획 이탈이 실패처럼 느껴진다 |

**시장 근거**: 2026년 6월 생활물가지수 +3.4%(전체 소비자물가 +3.2%보다 높음), 5년 누적 외식물가
20%+ 상승. 그런데도 2025년 배달 거래액은 37.6조 원(+12.4% YoY)으로 사상 최고 — 이 간극이
"마찰이 문제"라는 가설의 근거다.

### 기존 대안 (Existing Alternatives)

| 대안 | 왜 충분하지 않은가 |
|---|---|
| **배달 앱** (진짜 경쟁 상대) | 고민 자체를 없애주지만 돈이 나가고 재료는 계속 방치된다 |
| 레시피 검색 사이트 | "요리 이름"으로 검색하는 구조라 "가진 재료로 뭘 만드나"라는 역방향 질문에 약하다 |
| 절약 앱 (거지맵·마감할인) | 싸게 사 먹는 것을 돕지, 이미 가진 재료를 쓰게 하지는 않는다 |
| 프리미엄 스마트 냉장고 (삼성 비스포크 AI 패밀리허브) | 방향은 같지만 고가라 자취생이 살 수 없다. 게다가 오인식(당근→대파) 보정이 필요해 수동 입력을 완전히 없애지도 못한다 |
| 아무것도 안 하기 | 머릿속 기억에 의존 → 장벽 1이 그대로 남는다 |

## ③ 고유의 가치 제안 (UVP)

> **냉장고에 있는 대로, 오늘 한끼 완성.**

- **하이컨셉 피치**: "스마트 냉장고를 살 필요 없이, 있는 냉장고 그대로." 비교 대상은 삼성이 아니라
  지금까지 아예 추적을 안 하던 사용자 자신이다.
- **진짜 파는 것**: "AI가 레시피를 추천해준다"는 기능이 아니라, 원래 갖고 있던 **식비 절약 욕망을
  실현 가능하게 만드는 것**. 장벽을 없애 배달 대신 요리를 선택하게 한다.
- **차별점**: "가진 재료 → 즉시 요리 결정"을 배달만큼 빠르게.
- **정직성 원칙**: "이 서비스가 당신의 생활비를 아껴줬다"고 주장하지 않는다. 사용자 본인이 오늘
  요리를 선택한 결과를 그대로 되비춰줄 뿐이다. "강력한 AI 기반 식단 솔루션" 같은 과장 문구는 쓰지 않는다.

## ④ 솔루션 (Solution)

| 문제 | 대응 | 상태 |
|---|---|---|
| 냉장고 파악 안 됨 (장벽 1) | 재료 입력 → AI 추천 (`recipe.html`) | ✅ 구현 완료 |
| 장보기 계획 부재 + 배송 지연 (장벽 2·3) | 재료함 기반 주간 식단 계획 + 부족분만 뽑는 장보기 리스트 (`mealplan.html`, `shopping.html`) | ✅ 구현 완료 |
| 산 것/먹은 것 추적 비대칭 (심층 1) | "이거 해먹었어요" → 쓰인 재료 자동 차감 + 나머지 계획 재검증 | ✅ 구현 완료 |
| 욕망은 있는데 행동으로 안 이어짐 (심층 2) | 절약 체감 카운터 — 주간·월간·누적, "치킨 O마리 값" 단위 병기 | ✅ 구현 완료 |
| 고정 계획 = 실패로 느껴짐 (심층 3) | 요일 고정 → 후보 풀 전환 | 📄 스펙 완료, 미구현 |
| 추천 신뢰도 (100% AI 생성) | KADX 레시피 233,283건과 먼저 매칭, 실패 시에만 AI 폴백 (2,233ms → 216ms) | ✅ 구현 완료 |

**설계 원칙**: 냉장고를 단일 출처(single source of truth)로 두고, 모든 화면이 같은 재료함을 읽고 쓴다.
절약 카운터는 숫자가 **오직 올라가기만** 해서 배달 시킨 날에도 죄책감을 주지 않는다(MDA 프레임워크 —
메커닉: 고정 단가 누적, 다이나믹: 과거의 나와 비교, 에스테틱: 뿌듯함).

## ⑤ 채널 (Channels)

- **현재 (사실)**: Vercel 배포 URL 직접 공유, GitHub 공개 저장소.
- **[가정]** 자취·절약 커뮤니티(에브리타임, 자취 관련 커뮤니티) 공유 / "냉장고 재료 요리" 검색 유입 /
  사용자가 절약액 카드를 캡처해 공유하는 바이럴.
- 어느 것도 아직 검증되지 않았다. 방문자 카운팅조차 미구현이라 현재는 유입 경로를 관측할 수단이 없다.

## ⑥ 수익원 (Revenue Streams)

- **현재**: 없음. 전액 무료, 학습 미션 결과물.
- **[가정] 후보**: 장보기 리스트 → 커머스 제휴 링크 / 프리미엄(가족 계정, 대용량 재료함) / 마감할인 제휴.
- ⚠️ **제약**: 현재 레시피 매칭에 쓰는 KADX 데이터는 CC BY-NC-ND(비영리) 조건이다. **수익화 시점에는
  이 데이터를 못 쓰므로 별도 데이터 소싱이 선행되어야 한다.**

## ⑦ 비용 구조 (Cost Structure)

- **OpenAI API 호출** — 가장 큰 변동비. 편집할 때마다 자동 호출하지 않고 사용자가 호출 시점을 정하도록
  설계한 이유가 여기에 있다. KADX 선매칭으로 AI 호출 자체를 줄인 것도 같은 맥락이다.
- **Vercel 호스팅** — 현재 무료 티어. 서버리스 함수 실행 시간에 비례.
- **저장소 비용 0** — 계정·서버 DB 없이 `localStorage`만 쓴다. 대신 지표 수집이 불가능하다는 대가를 치른다.
- **수익화 시 신규 발생**: 레시피 데이터 라이선스 재소싱 비용.

## ⑧ 핵심 지표 (Key Metrics)

해적 지표(AARRR) 중 이 서비스가 실제로 봐야 할 것:

| 단계 | 지표 | 현재 측정 가능? |
|---|---|---|
| Activation | 재료를 넣고 추천을 한 번 받아본 사용자 | ❌ |
| **Retention (핵심)** | 주 N회 재방문 — 하루 1~2끼 반복 수요를 잡았는지 | ❌ |
| Revenue 대리지표 | **누적 절약액**(주간·월간) — 배달 대신 요리를 선택한 횟수 × 고정 단가 | ⚠️ 기기 안에서만 |
| 행동 완결 | "이거 해먹었어요" 실행 횟수 = 실제 요리로 이어진 비율 | ⚠️ 기기 안에서만 |

> ⚠️ **지금은 어느 것도 서비스 차원에서 관측할 수 없다.** `localStorage`만 쓰는 구조라 절약액은 사용자
> 개인 기기 안에만 쌓인다. "자취생 평균 한 달 OO원 절약" 같은 숫자는 실사용 데이터가 쌓이기 전에는 쓰지 않는다.
> 가장 먼저 해소해야 할 캔버스 항목이다 (기획서의 "방문자 수 간단 카운팅" 확장 아이디어).

## ⑨ 경쟁 우위 (Unfair Advantage)

- **있는 것**: 기획자가 곧 타겟이라 문제를 직접 겪는다는 이해도. 그리고 구매↔소비를 양방향으로 추적해
  냉장고를 단일 출처로 유지하는 데이터 구조 — 쓸수록 개인 재료·식습관 데이터가 쌓여 추천이 정확해진다.
- **없는 것 (정직하게)**: 기능 자체는 복제하기 쉽다. 특허도, 네트워크 효과도, 사용자 기반도, 독점
  데이터도 없다. 현재 시점의 진짜 방어벽은 "축적된 개인 재고 데이터에서 오는 전환 비용"뿐이고, 그것도
  `localStorage`에 있어 기기를 바꾸면 사라진다.

## 아직 답이 없는 빈틈

1. **배달앱의 절대적 편의성("그냥 누르면 끝")을 이길 답이 없다.** 지금 있는 솔루션은 전부 이 서비스
   안의 마찰을 줄이는 것이지, 배달앱보다 쉬워지는 것은 아니다. 절약 체감이 가장 유력한 후보지만 미검증.
2. **이미 여러 절약 도구를 조합해 쓰는 사용자의 관심(attention) 안에서 매일 켜야 하는 자리를 차지할 수
   있는가.** 경쟁 상대를 배달 앱과 스마트 냉장고로만 정의했는데, 실제로는 다른 절약 앱들과도 시간을 나눈다.
3. **지표 측정 수단 자체가 없다.** ⑤채널·⑧핵심 지표 두 칸이 비어 있는 근본 원인이며, 나머지 가설을
   검증하려면 이것부터 풀어야 한다.

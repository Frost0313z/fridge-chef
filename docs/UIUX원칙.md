# UI/UX 원칙 — 냉털 셰프 (fridge-chef)

이 문서는 새로 정한 규칙이 아니라, **이미 코드에 반영돼 있는 판단들을 사후에 언어화한 것**입니다.
기능을 붙일 때마다 그때그때 내린 결정이 몇 가지 일관된 기준을 따르고 있었고, 그 기준을 적어두지 않으면
다음 기능에서 다르게 판단하게 되므로 정리했습니다.

원칙은 **세 개의 축**으로 나눕니다.

| 축 | 묻는 질문 | 실패하면 |
|---|---|---|
| [A. 안전](#a-안전-축--해를-끼치지-않는다) | 사용자에게 해를 끼치지 않는가 | 화면이 멈추고, 잘못된 정보를 주고, 원치 않는 일이 일어난다 |
| [B. 배려](#b-배려-축--실제로-돕는다) | 사용자를 실제로 돕는가 | 해는 없지만 아무도 쓰지 않는다 |
| [C. 디자인](#c-디자인-축--설명-없이-이해된다) | 화면이 스스로를 설명하는가 | 기능은 있는데 찾지 못하고, 눌러도 되는지 몰라 안 누른다 |

세 축은 별개입니다. A를 아무리 잘해도 B가 비면 "안전하게 쓸모없는" 서비스가 되고,
A·B가 있어도 C가 비면 그 가치가 화면에 전달되지 않습니다.

이 문서는 판을 거듭하며 축이 늘었습니다. 첫 판은 A축뿐이었고 — 원칙이 전부 "무엇이 잘못될 수 있는가"에서
출발한 개발자의 렌즈였습니다. 두 번째 판에서 B축을 분리했고, 세 번째 판에서 C축을 더했습니다.

[D. 체크리스트](#d-체크리스트)는 세 축 모두에서 아직 지키지 못한 항목이며, 그대로 다음 작업의 목록입니다.

# A. 안전 축 — 해를 끼치지 않는다

## A1. 애매하면 안전한 쪽으로 틀린다

> 판정이 불확실할 때는 **실패 비용이 싼 쪽으로** 틀리게 만든다.

장보기 리스트는 *식단 재료 − 재료함*으로 계산하는데, `"파"`와 `"파프리카"`처럼 이름이 겹치는 경우
보유 여부를 확실히 알 수 없습니다. 이때 두 방향의 오류는 비용이 전혀 다릅니다.

| 틀리는 방향 | 결과 | 비용 |
|---|---|---|
| 필요한 걸 안 사게 됨 | 그날 그 요리를 못 만듦 | **치명적** |
| 이미 있는 걸 또 사게 됨 | 돈이 조금 더 듦 | 감수 가능 |

그래서 `isCovered()`는 짧은 쪽이 1글자면 포함 매칭을 인정하지 않고, 애매한 항목을 리스트에 **남기는**
쪽으로 기웁니다.

> [!NOTE]
> 이 원칙에는 한계가 있습니다. 사용자 입장에서는 "또 사는 것"도 실패입니다.
> 추측의 방향을 고르는 대신 **한 번 물어보면** 두 실패를 모두 피할 수 있습니다 — [B8](#b8-애매하면-추측하지-말고-묻는다) 참고.
> A1은 묻지 않기로 했을 때의 차선책이지, 최선이 아닙니다.

**적용**: `js/mealplan.js` — `isCovered()`

<br>

같은 기준이 빈 재료함 처리에도 적용됩니다. 재료함이 비면 걸러낼 대상이 없어 식단의 모든 재료가
리스트에 담기는데, 이건 버그가 아니라 옳은 결과입니다(가진 게 없으면 다 사야 하니까).
그래서 제출을 막지 않고 **문구만** 사실에 맞춥니다 — 막으면 첫 방문자가 서비스를 아예 써볼 수 없습니다.

**적용**: `js/mealplan.js` — `renderShoppingList()`의 재료함 유무 분기

## A2. 실패해도 멈추지 않고, 원인별로 다르게 말한다

> 화면은 어떤 실패에서도 멈추지 않는다. 그리고 **사용자가 할 수 있는 행동**을 원인별로 다르게 안내한다.

| 상황 | 처리 | 이유 |
|---|---|---|
| 빈 입력 | 프론트에서 차단 (서버도 재검증) | API 호출 비용을 아낀다 |
| API 오류(4xx/5xx) | 서버가 502로 통일, 원인은 감춤 | 사용자가 OpenAI 내부 사정을 알 필요가 없다 |
| 응답 지연 | 서버 15초 · 클라이언트 20초(식단 25초) 이중 타임아웃 | 서버가 먼저 끊어도 클라이언트가 무한 대기하지 않는다 |
| 네트워크 단절 | `AbortError` 여부로 "지연"과 "연결 확인"을 구분 | 사용자가 취할 행동이 다르다 |

**적용**: `api/recommend.py` · `api/mealplan.py`의 예외 → HTTP 상태 매핑, `js/shared.js` — `postJson()`

### 사용자에게 보여줄 문구는 서버가 정한다

오류 응답의 스펙 자체에 이 규칙이 박혀 있습니다.

```python
응답(4xx/5xx): {"error": str, "message": str}  # message는 화면에 그대로 표시할 한국어 안내문
```

프론트는 `data.message`를 그대로 띄우고, 없을 때만 기본 문구로 대체합니다.

**적용**: `api/recommend.py` 상단 docstring, `js/shared.js` — `postJson()`

## A3. 자동화는 결제 직전에서 멈춘다

> 사용자 대신 **돈을 쓰는 행동**은 하지 않는다.

주간 식단의 장보기 리스트는 쿠팡 검색 링크만 제공하고 장바구니에 자동으로 담지 않습니다.
기술적 제약(개인이 쓸 수 있는 공식 장바구니 API가 없음)만이 아니라, 가능한 우회 방법(로그인 세션 자동화)이
이용약관 위반 소지가 있고 실제 결제로 이어질 수 있어서 범위를 의도적으로 제한했습니다.
이 제한은 숨기지 않고 화면과 FAQ 양쪽에 명시합니다.

**적용**: `js/mealplan.js` — `renderShoppingList()`, `index.html` FAQ

## A4. 되돌릴 수 없는 것에만 마찰을 넣는다

> 확인창은 일괄 적용하지 않는다. **복구 비용에 비례해서** 넣는다.

| 동작 | 확인창 | 이유 |
|---|---|---|
| 추천 이력 전체 지우기 | ✅ `confirm()` | 여러 건이 한 번에 사라지고 되돌릴 수 없다 |
| 식단 계획 지우기 | ✅ `confirm()` | AI 호출로 만든 결과가 통째로 사라진다 |
| 재료함 개별 삭제 (`×`) | ❌ 없음 | 하나 잘못 지워도 다시 입력하면 그만이다 |

**적용**: `js/recipe.js` — `initHistory()`, `js/mealplan.js` — 계획 지우기, `js/shared.js` — `initPantry()`

## A5. 저장하되 서버로 보내지 않는다

개인화를 계정·서버 DB 없이 `localStorage`만으로 구현합니다. 로그인 없는 서비스라는 구조를 유지하기 위한
선택이고, 대신 **무엇이 어디에 저장되고 어떻게 지우는지**를 FAQ에 명시합니다.

**적용**: `js/shared.js` — `loadJson`/`saveJson`, `index.html` FAQ

## A6. 입력은 관대하게, 출력은 엄격하게

> 사용자와 AI에게서 **받을 때는 최대한 받아주고**, 화면에 그리기 전에 엄격하게 정제한다.

| 방향 | 태도 | 구현 |
|---|---|---|
| 사용자 → 시스템 | 정확한 계량 불필요, 자유 텍스트, `계란 2개`·`두부(반모)` 아무 표기나 | `normalizeIngredient()` — 괄호·수량·단위 22종 제거 |
| AI → 시스템 | JSON 강제 후에도 **구조는 못 믿는다** | `sanitize_recipes()` / `sanitize_plan()` |
| 저장소 → 시스템 | 사용자가 직접 고쳤거나 옛 버전 값이 남아 있을 수 있다 | `loadJson()`의 fallback |
| 시스템 → 화면 | 무엇이 들어오든 이스케이프 | `escapeHtml()` — 재료명이 `aria-label` 속성값에도 들어가므로 따옴표까지 |

`response_format={"type": "json_object"}`는 **JSON이라는 것만** 보장하고 구조는 보장하지 않습니다.
"프론트는 서버 응답의 형식을 믿어도 된다"는 경계를 서버에 두어, 렌더링 코드마다 방어 코드를 흩뿌리지 않습니다.

**적용**: `api/*.py` — `to_str_list`/`sanitize_*`, `js/shared.js`, `js/mealplan.js`

## A7. 구조와 표현의 일관성

- **왼쪽 끝을 맞춘다** — `.page`는 헤더와 같은 폭(`--max-width: 1080px`), 글줄이 길면 읽기 어려운 요소만
  `max-width: 680px`로 좁히되 **`margin: auto`로 다시 가운데 정렬하지 않는다.** 그러면 헤더 로고와
  본문 제목의 왼쪽 시작선이 어긋납니다.
- **색은 토큰으로만 지정한다** — 다크 모드가 `:root[data-theme="dark"]`의 토큰 오버라이드로 동작하므로,
  하드코딩한 색은 그 요소만 테마를 따라가지 않습니다.
- **화면을 보지 못해도 흐름이 끊기지 않는다** — 본문 바로가기 링크, 로딩 `role="status"`,
  결과 `aria-live="polite"`, 오류 `role="alert"`, 닫힌 모바일 메뉴 `visibility: hidden`
  (`max-height: 0`만으로는 Tab 대상으로 남음), Esc 닫기 시 토글로 포커스 복귀,
  `:focus-visible` 전역 아웃라인, `prefers-reduced-motion` 존중.

**적용**: `css/style.css`

## A8. 읽히지 않는 글자는 없는 글자다

색 대비는 취향이 아니라 **안전 축**입니다. 아무리 좋은 문구를 써도 읽히지 않으면 전달되지 않고,
그 손해는 조명이 밝은 곳에 있거나 시력이 약한 사용자에게만 집중됩니다.

**기준** (WCAG 2.1 AA)

| 대상 | 필요한 대비 |
|---|---|
| 본문 글자 (24px 미만, 굵은 글씨는 18px 미만) | **4.5:1** |
| 큰 글자, 아이콘, 포커스 링 | **3:1** |

**규칙**

- **라이트·다크 두 모드를 모두 계산한다.** 한쪽만 맞으면 통과가 아닙니다.
- **주황은 역할에 따라 값이 다르다.** 채움(`--color-primary`)은 밝아도 되지만,
  글자와 포커스 링(`--color-primary-dark`)은 배경과 4.5:1을 넘겨야 합니다. 같은 토큰으로
  두 역할을 겸하면 반드시 한쪽이 미달합니다.
- **밝은 채움 위에는 흰 글자를 올리지 않는다.** `--color-on-primary`(잉크)를 씁니다.
  밝은 주황 위 흰 글자는 2.59:1로, 큰 글자 기준 3:1도 못 넘깁니다.

**2026-08-12에 고친 것** — 외부 디자인 기준(hallmark)으로 점검하다 발견했습니다.
이 문서에 대비 기준이 없어서 가장 눈에 띄는 요소들이 미달인 채 남아 있었습니다.

| 대상 | 전 | 후 |
|---|---|---|
| 주 CTA 버튼·단계 번호 (흰 글자 → 잉크) | 2.59:1 · 다크 2.32:1 | **5.95:1** · 다크 6.63:1 |
| 주황 링크·강조 글자 `#e05e2b` → `#b8501f` | 3.43:1 | **4.74:1** |
| 포커스 링 (`--color-primary` → `-dark`) | 2.45:1 | **4.74:1** |
| 오류 문구 `#d64545` → `#b32d2d` | 3.83:1 | **5.52:1** |

**적용**: `css/style.css` — `:root` 토큰

# B. 배려 축 — 실제로 돕는다

## 기준선은 배달앱이다

[기획서](./서비스기획서.md)는 이 서비스의 **진짜 경쟁 상대를 다른 레시피 서비스가 아니라 배달앱**으로 규정했습니다.
그렇다면 배려의 기준선도 배달앱입니다. 배달앱은 열자마자 선택지를 주고, 지난 주문을 버튼 하나로 반복하게 하고,
도착 시간을 분 단위로 알려주고, 결정한 뒤부터 음식이 도착할 때까지 사용자를 놓지 않습니다.

**"안전하지만 배달앱보다 불친절하면 사용자는 배달앱을 연다."** 이 축의 원칙은 전부 여기서 나옵니다.

## 이미 지키고 있는 것

먼저 공정하게 — 지금도 배려인 것들이 있습니다.

| 배려 | 어디에 |
|---|---|
| 정확한 계량을 요구하지 않음 | `index.html` FAQ, 프롬프트 |
| 소금·후추·기름·물은 없어도 있다고 쳐줌 | `api/recommend.py` — `SYSTEM_PROMPT` |
| 알려주지 않은 값비싼 재료를 임의로 추가하지 않음 | 같은 곳 |
| 자주 쓰는 재료를 매번 다시 타이핑하지 않게 함 | 재료함 (`js/shared.js`) |
| 분량·건강 여부를 **제출하지 않아도** 기억 | `js/recipe.js` — `change` 이벤트마다 저장 |
| 건강 관리 중이면 추천 성격을 바꿈 | `HEALTHY_HINT` |
| **묻지 않아도 되는 건 묻지 않음** — 혼자 사는 자취생이라는 전제는 선택지가 아니라 시스템 프롬프트 | `api/*.py` — `SYSTEM_PROMPT` |
| 이력 클릭은 API를 다시 부르지 않아 즉시 뜸 | `js/recipe.js` — `initHistory()` |
| 장을 봐서 재료함을 채우면 저장된 계획의 살 것이 자동으로 줄어듦 | `js/mealplan.js` — 복원 시 재계산 |
| 오류·로딩 문구가 기계적이지 않음 | "🍳 재료를 살펴보고 요리를 고민하고 있어요..." |

**공통점**: 전부 **재료를 입력하기까지**의 배려입니다. 아래 원칙들은 그 이후가 비어 있다는 이야기입니다.

## B1. 빈 화면 앞에 세워두지 않는다

> 첫 화면에서 사용자가 "뭘 해야 하지"를 고민하게 만들지 않는다.

첫 방문자는 빈 재료함과 빈 입력란을 마주합니다. `placeholder`에 예시가 있지만 읽고, 이해하고,
자기 냉장고를 떠올려 타이핑해야 합니다. 배달앱은 열자마자 누를 수 있는 카드를 보여줍니다.

**현재**: ✅ 해결됨 — 냉장고가 비어 있으면 눌러서 바로 넣는 예시 칩(계란·대파·두부·김치·양파)을
보여준다. 첫 방문자가 `placeholder`를 읽고 자기 냉장고를 떠올려 타이핑하는 단계를 건너뛴다.

## B2. 이미 알려준 것을 다시 기억하게 하지 않는다

> 서비스가 아는 정보를 사용자 머릿속에서 다시 꺼내게 하지 않는다.

가장 큰 모순입니다. 추천 카드의 재료 목록은 그냥 나열만 합니다 — 사용자는
`계란 2개 / 대파 / 두부 / 양파` 를 보고 **양파가 자기한테 있는지를 직접 기억해내야** 합니다.
재료함에 뭐가 있는지 서비스는 이미 알고 있는데도요.

주간 식단에서는 이 대조를 공들여 구현해놓고(당시 `computeShoppingList`), 정작 레시피 추천에서는
하지 않습니다. `isCovered()`가 이미 있으므로 새로 만들 것도 없습니다.

**현재**: ✅ 해결됨 — 추천 카드가 냉장고와 대조해 보유 재료는 흐리게, 미보유는 "사야 해요"로 표시한다.
판정은 `isCovered()`이고 `js/shared.js`에 있다. **렌더 시점마다 다시 계산**해 이력으로 과거 요리를

표시 자체를 생략한다.

> 이후 장보기 목록은 이름 대조를 그만두고 **서버가 수량까지 따져** 만드는 방식으로 바뀌었습니다
> (2026-08-11). "계란 2개"가 있어도 5일치에 8개가 필요하면 사야 하는데, 이름 매칭으로는 그 구분이
> 불가능했기 때문입니다. 그래서 지금 `isCovered()`를 쓰는 곳은 추천 카드 하나뿐이고, 두 화면의

얼마나 지났는지, 그리고 언제 포기하는지. 차오르는 것은 작업량이 아니라 그 마감까지입니다.

숫자는 1초마다 바뀌므로 `aria-live` 영역 **밖**에 두고 `aria-hidden` 처리했습니다. 안에 두면
화면을 읽어주는 사용자에게 1초에 한 번씩 읽힙니다. 그쪽에는 마감의 75%가 지난 시점에
"20초까지 기다린 뒤에도 답이 없으면 알려드릴게요"를 **한 번만** 알립니다.

## B5. 결과는 부엌까지 따라간다

**직접 만드는 것의 우선순위를 내렸다.** 앱 안에서 요리를 끝까지 안내할지는 서비스 성격

## C1. 개발자가 아닌 사용자 측면에서 만든다 ⚠️

- "가족 식사"는 제거, "자취생 간단요리"는 선택지가 아니라 **기본값**이므로 시스템 프롬프트로 승격
- "인원수"는 기능이 아니라 이름이 틀린 경우였습니다. 자취생도 2인분을 만듭니다(내일 점심용).
  `3~4인분` → `3~4끼 분량`으로 바꾸니 같은 값이 타겟의 언어가 되었습니다

**남은 것**

- **기술 스택 섹션 (해결됨)** — 소개 페이지 4개 섹션 중 하나를 차지하던 것을, 홈 통합 시

  필요한 정보는 아니지만 궁금한 사람은 펼쳐 볼 수 있습니다.
- **오류 문구 3개 (해결됨, 2026-08-13)** — 시스템의 언어였습니다. "요청 형식이 올바르지 않아요"는
  이해도 조치도 불가능했고, "서버에 API 키가 설정되어 있지 않아요"는 사용자 잘못이 아닌 것을
  사용자에게 말했으며, "AI 응답을 해석하지 못했어요"의 "해석"은 기술 용어였습니다.

  | 이전 | 현재 |
  |---|---|
  | 요청 형식이 올바르지 않아요. | 요청이 제대로 전달되지 않았어요. **페이지를 새로고침한 뒤** 다시 시도해주세요. |
  | 서버에 API 키가 설정되어 있지 않아요. | 지금은 AI가 답을 만들지 못해요. **사용자 잘못이 아니라 저희 쪽 문제예요.** 조금 뒤에 다시 시도해주세요. |
  | AI 응답을 해석하지 못했어요. | AI가 답을 제대로 만들지 못했어요. **한 번 더 시도하면 대개 잘 나와요.** |

  셋 다 "무엇이 일어났는가"가 아니라 **"무엇을 하면 되는가"로 끝나게** 고쳤습니다.
  원인 구분은 화면 문구가 아니라 응답의 `error` 코드가 계속 담당하므로, 개발자가 잃는 정보는
  없습니다([A2](#a2-실패해도-멈추지-않고-원인별로-다르게-말한다)의 "문구는 서버가 정한다"와 같은 자리).

## C2. 각 화면은 한 가지 행동에 집중하게 한다 ❌

**해결됨 (2026-08-11 책임 단위 재편).** `recipe.html`은 한 스크롤에 섹션이 4개였고 주 행동이 한가운데 있었습니다.

① 내 재료함        ← 등록하기      ▸ 접힘 (개선)
② 추천 폼          ← 추천받기   ★ 진짜 주 행동
③ 결과
④ 최근 추천 이력   ← 지난 것 보기

1차로 재료함을 `<details>`로 접어 완화했지만 섹션 수 자체는 그대로였습니다. 2차로 **책임 단위로
페이지를 나눴습니다** — 재료 편집은 냉장고(`pantry.html`), 장보기는 `shopping.html`로 독립시켜
각 화면이 하나의 행동만 갖게 했습니다.

편집 UI가 한 곳으로 모이면서, 나머지 화면에는 **조회 전용 바**만 남았습니다.
**C2는 행동이 하나여야 한다는 것이지 정보가 하나여야 한다는 게 아니므로** 이 바는 위배가 아닙니다.

## C3. 반응을 보여준다 ✅

  줄입니다. 2026-08-11에 한 번 ✅로 적었지만 그때는 **이미 있는 재료에 아무 반응이 없어**
  실제로는 닫히지 않은 고리였습니다.
- 레시피 추천과 주간 식단을 오가는 유도가 홈에만 있습니다.

## C5. 시각적 일관성을 유지한다 ⚠️

> 같은 의미는 같은 모양으로 보여야 한다.

현재 값 분포를 세어보면 규칙이 아니라 그때그때 정한 값들입니다.

```
border-radius:  10px×7 · var(--radius)×3 · 50%×3 · 999px×2 · 12px · 4px · 2px      → 7종
font-size:      0.8 / 0.85 / 0.88 / 0.9 / 0.92 / 0.95 / 1 / 1.05 / 1.1 / 1.15 / 1.2 / 1.8rem  → 12종
```

`--radius: 14px` 토큰이 있는데 하드코딩 `10px`가 7곳으로 더 많습니다. 0.88·0.9·0.92rem이 공존하는 건
의도한 위계가 아닙니다. spacing 토큰은 아예 없습니다.

- **같은 위계의 `h2`가 두 크기** — `.page h2` 1.2rem vs `.pantry h2`·`.shopping-list-section h2`·`.history-header h2` 1.1rem
- **카드 padding 제각각** — feature-card `28px 22px`, recipe-card `20px`, mealplan-day-card `18px`
- **다크 모드 깨짐 (해결됨)** — `.error-message`의 `border: 1px solid #f4c2c2`가 전체에서 유일하게
  토큰을 쓰지 않아, 다크 배경 위에 밝은 분홍 테두리가 그대로 떴습니다.
  `--color-danger-border` 토큰을 light/dark에 각각 추가해 교체했고, 이로써 토큰을 쓰지 않는
  색이 사라져 [A7](#a7-구조와-표현의-일관성)의 "색은 토큰으로만"이 다시 참이 되었습니다.
- **죽은 코드** — `.required` 클래스가 CSS에 있으나 HTML 4개 어디에도 없습니다.

## C6. 예상할 수 있어야 한다 ⚠️

> 누르기 전에 무슨 일이 일어날지 알 수 있어야 한다.

**해결됨** — 재료함의 "추가" 버튼이 주 CTA와 같은 `--color-primary` 채움이라 위계가 같았습니다.
보조 CTA와 같은 언어(surface 배경 + inset 윤곽선)로 낮춰, 이제 화면의 주황 채움은 제출 버튼 하나뿐입니다.

**남은 것**

- `.mealplan-clear-btn`이 `hidden` 해제와 함께 제출 버튼 아래에 **예고 없이 나타납니다.**
- 이력 항목이 `<button>`인데 카드처럼 생겨서, 누르면 결과 영역이 바뀐다는 걸 예측하기 어렵습니다.

## C7. 의미 있는 움직임만 보여준다 ✅

> 움직임은 장식이 아니라 상태 변화를 알리는 수단이다.

**대체로 지켰습니다.** 전체 transition이 3개(body 색 `0.15s`, 버튼 `0.15s`, 메뉴 `0.2s`)뿐이고,
`@keyframes` 애니메이션은 0개이며, `prefers-reduced-motion`에서 전부 제거됩니다.

초기 구현은 **움직임의 배치가 반대**였습니다 — 인지되지 않는 버튼 hover의 `translateY(-1px)`는 있고,
15~25초 걸려 도착한 결과 카드에는 전환이 없었습니다. hover 이동은 제거하고, 결과 카드
(`.recipe-card`·`.mealplan-day-card`)에만 0.2s 페이드인을 넣어 "도착했다"는 신호로 씁니다.

`@keyframes`는 이 하나뿐이고, `transform`도 여기서만 씁니다.

## C8. 누구나 이해하기 쉬운 글을 제공한다 ⚠️

> 읽고 나서 무엇을 해야 할지 알 수 있어야 한다.

**지킨 것**: 전체 "~해요"체 통일, "재료를 1개 이상 입력해주세요",
"재료함만으로 충분해요! 따로 살 재료가 없어요 🎉".

**해결됨**: [C1](#c1-개발자가-아닌-사용자-측면에서-만든다-)의 오류 문구 3개(2026-08-13)와 기술 스택 섹션.
"냉털" 뜻풀이는 히어로 아래 한 줄로 옮겨, 첫 화면에서 바로 읽힙니다.

## C9. 사용자의 익숙함을 존중한다 ✅

> 이미 아는 방식대로 동작해야 한다. 새 관례를 발명하지 않는다.

**지킨 것**: `<select>` 기본 스타일 유지, `×` 삭제, 우측 상단 "전체 지우기",
외부 링크 새 탭 + `rel="noopener noreferrer"`, 재료함 접기에 네이티브 `<details>` 사용.

**해결됨 — 모바일 관례**

| 항목 | 이전 | 현재 |
|---|---|---|
| `.pantry-chip-remove` 터치 타겟 | 20×20px | 보이는 크기 32px + `::after` 오버레이로 **히트 영역 44×44px** |
| 모바일 제출 버튼 | `align-self: flex-start`로 좁게 왼쪽 정렬 | 640px 이하에서 full-width |

터치 타겟을 넓히면 오버레이가 좌우로 6px씩 넘치므로 `.pantry-chips`의 `gap`도 8px → 12px로
함께 올렸습니다. 그러지 않으면 인접 칩의 히트 영역이 겹칩니다(555px 뷰포트에서 미겹침 확인).

## C10. 필요한 만큼만 단순하게 디자인한다 ⚠️

> 요소를 늘리기 전에 뺄 수 있는지 먼저 본다.

> [!IMPORTANT]
> **"필요한 만큼만"은 "최소로"가 아닙니다.** 이 문서에서 두 번의 반대 방향 변경이 모두 이 원칙을
> 근거로 삼았는데, 서로 모순되지 않습니다.
> - 소개 → 홈 통합 (페이지 4→3): **중복 제거** — 같은 말을 두 번 하고 있었다
> - 냉장고·장보기 분리 (페이지 3→5): **책임 분리** — 한 화면이 여러 일을 하고 있었다
>
> 판단 기준은 페이지 개수가 아니라 "이 화면이 몇 가지 일을 하는가"입니다.

**지킨 것**: 프레임워크 없이 빌드 도구 없이 구현 — 현 규모에 적절합니다.

**어긋난 곳**: **이모지가 12종 이상**입니다(🧊 🥕 🤖 🛒 📖 🕘 🗓️ ⏱ 🍳 🎉 💼 ✉️).
톤은 살지만 전부 강조되면 아무것도 강조되지 않습니다 — 결과 카드의 `⏱`와 섹션 제목의 `🥕`가
같은 비중으로 보입니다. 사용 자리를 정해야 합니다(예: 섹션 제목에만).

토큰 체계도 절반만 있습니다 — `--radius`·`--header-height`는 있는데 spacing·font-size 스케일이 없어
하드코딩이 난립합니다([C5](#c5-시각적-일관성을-유지한다-)).

여기를 같이 고치는 것을 잊으면 그 데이터만 조용히 안 따라옵니다 — 냉장고 예시 목록이
두 곳에 적혀 있어 갈라졌던 것([D-0o](#d-0o-완료-2026-08-17--예시-버튼과-재료-칩을-눈으로-갈라놓기))과 같은 종류의 사고입니다.
값은 파싱하지 않고 **저장된 문자열 그대로** 담습니다. 읽어서 다시 쓰는 과정이 없으면
되돌릴 때 원본과 한 글자도 달라지지 않습니다.

`{ version: 1, exportedAt, data }`로 감쌉니다. 스키마가 바뀔 수 있는데 파일에 버전을
적어두지 않으면 나중에 옛 파일을 읽을 때 무엇이 다른지 알 방법이 없습니다.

**실측 (2026-08-17)**: 7개 키(pantry·mealplan·history·prefs·favorites·savings·theme)를
내보내고, 저장소를 비운 뒤 그 파일로 되살려, **다시 내보낸 결과가 원본과 완전히 일치**하는 것을
확인했습니다. 취소를 누르면 아무것도 지우지 않고 `"가져오기를 멈췄어요. 지금 기록은 그대로예요."`로 끝납니다.

## D-0r. 완료 (2026-08-17) — 지시가 아니라 코드로 막는다 (재료 검증)

[A6](#a6-입력은-관대하게-출력은-엄격하게)의 "AI → 시스템: 구조는 못 믿는다"를 **내용**까지 넓힌 항목입니다.
`SYSTEM_PROMPT`는 "알려주지 않은 재료를 임의로 추가하지 마세요"라고 **지시만** 하고,
지켜졌는지 확인하는 코드가 없었습니다. 장보기 합산을 AI에게 맡겼다가 34종 중 6종을
놓쳤던 것과 같은 종류의 문제입니다 — 맡길 것과 확인할 것의 경계가 잘못 그어져 있었습니다.

`sanitize_recipes()`가 레시피의 재료를 사용자 재료 + 기본 조미료와 대조해, 벗어난 재료가
섞인 레시피를 버립니다. "같은 재료인가"를 판단하는 규칙은 장보기가 쓰던 `find_owned()`를
그대로 씁니다 — 규칙이 갈라지면 한 화면은 있다고 하고 다른 화면은 없다고 하게 됩니다.
`BASIC_SEASONINGS`도 `api/_common.py` 한 곳에 두어, 추천이 "써도 된다"고 보는 재료와
장보기가 "사러 갈 일 없다"고 보는 재료가 갈라지지 않게 했습니다.

| 할 일 | 원칙 | 결과 |
|---|---|---|
| 프롬프트 지시를 강제하는 코드가 없음 | [A6](#a6-입력은-관대하게-출력은-엄격하게) | ✅ 벗어난 재료가 섞인 레시피를 버린다 |
| 같은 판정 규칙이 파일마다 따로 | [A7](#a7-구조와-표현의-일관성) | ✅ `find_owned`·`BASIC_SEASONINGS`를 한 곳에서 공유 |
| 검증이 결과를 통째로 없앨 수 있음 | [B7](#b7-막다른-길을-만들지-않는다) | ✅ 전부 걸리면 거른 것을 그대로 돌려준다 |

**검토에서 걸러낸 것 (2026-08-17, 실측)**

처음 구현은 레시피 쪽 재료의 수량을 떼지 않고 비교해서, 실제로 나올 법한 표기 11가지 중
**4가지가 잘못 버려졌습니다.**

| 사용자 재료 | 레시피 재료 | 버려진 이유 |
|---|---|---|
| 계란, 밥 | 계란 2개, **물 1컵**, 소금 | `find_owned`는 짧은 쪽이 한 글자면 우연한 겹침으로 보고 거절한다. 물·밥·쌀은 수량이 붙는 순간 영영 못 알아본다 — 찌개·국·찜이 전부 여기 해당한다 |
| 계란, 대파 | …, **후춧가루 약간** | 사이시옷 때문에 "후추"가 부분 문자열이 아니다 |
| 계란, 김치 | …, **올리브오일 1큰술** | 목록에는 "올리브유"만 있었다 |
| 계란, 김치 | **달걀 1개**, 김치 | 같은 것을 다르게 부르는 이름은 글자 비교로 알 수 없다 |

앞의 셋은 고쳤습니다 — 레시피 쪽도 `parse_line`으로 수량을 떼서 **양쪽을 같은 방법으로**
다듬고, 조미료 목록에 표기 변형을 더했습니다. **네 번째(달걀/계란)는 못 고칩니다.**
이름 동의어는 글자 비교의 한계이고, 같은 한계가 화면의 "사야 해요" 판정(`isCovered`)에도
이미 있습니다([D-2 22번](#d-2-디자인-축에-남은-것)).

그래서 **전부 걸렸을 때는 거른 것을 그대로 돌려줍니다.** 빈 손으로 돌려보내면 화면은
"추천 결과를 만들지 못했어요. 재료를 다르게 입력해보세요"라고 **엉뚱한 원인**을 말하며
막다른 길이 됩니다([B7](#b7-막다른-길을-만들지-않는다)) — 사용자 입력은 멀쩡했는데 말입니다.
카드가 없는 재료에 "사야 해요"를 이미 붙이므로 속지도 않습니다.
검증은 결과의 질을 올리는 장치이지 결과를 없애는 장치가 아닙니다.

> [!NOTE]
> **식단의 빈 자리 채우기(`mealplan.py`의 `fill_missing_ingredients`)에는 같은 검증을 넣지
> 않았습니다.** 언뜻 같은 취약점처럼 보이지만 약속이 반대입니다 — 추천은 "지금 있는 것으로
> 만들 수 있는 요리"를 말하고, 이쪽은 "이 요리에 무엇이 드는가"를 말합니다. 사용자가 직접
> 적어 넣은 메뉴의 재료는 **없는 것까지 나와야** 장보기 목록이 만들어집니다. 여기에 냉장고
> 필터를 걸면 장보기가 늘 비게 되므로, 넣지 않는 것이 맞습니다.

**테스트**: `python api/test_handlers.py` 25 → 33개.

## D-0s. 완료 (2026-08-20) — 즐겨찾기 목록 모달

[D-0p](#d-0p-완료-2026-08-17--밀려나지-않는-목록-즐겨찾기)에 남겨둔 note를 닫습니다 —
"즐겨찾기 목록 자체를 보는 화면"이 이제 있습니다.

**배경**: 즐겨찾기(`loadFavorites()`)는 `mealplan.html`의 요일·끼니별 "넣기" 팝업 안에서만
노출됐습니다(`js/mealplan.js`의 `addPicksHtml()`). 전체를 한눈에 보려면 슬롯을 하나 열어야
해서, 즐겨찾기만 따로 훑어보고 이번 주 계획을 세우기가 불편했습니다.

**설계**: `mealplan.html`의 페이지 인트로에 "즐겨찾기 보기" 버튼(`.link-button`)을 추가 →
클릭 시 `<dialog>` 모달(`#favorites-dialog`)을 띄웁니다. `#meal-dialog`(요일 상세)와
`#pantry-import-dialog`(사진 등록 확인 화면)가 쓰던 `<dialog>` 패턴을 그대로 재사용했습니다
— 배경 막·초점 가두기·Esc 닫기 근거가 같은 세 번째 사용 사례입니다. 다른 두 모달은 440px
폭이지만 이건 목록+상세 두 칸을 담아야 해서 820px로 더 넓습니다. 이 화면 전용 스타일이라
클래스는 새로 만들되(`.favorites-dialog*`) 구조와 톤은 그대로 맞췄습니다.

**모달 안 내용 (2026-08-20 재설계 — 처음엔 단순 목록이었다가 당일 확장)**: 왼쪽은 고르는
목록(이름 + 조리 시간 + 기존 별 버튼), 오른쪽은 고른 요리의 상세 카드입니다. 상세 카드는
`recipe.js`의 `recipeCardHtml`과 같은 정보(이름·시간·재료·조리 순서·레시피 링크)를
보여줍니다 — 실제 매칭된 레시피(`recipeUrl` 있음)는 원문 링크를, 그렇지 않으면 담아둘
때 함께 저장한 조리 순서와 검색 링크를 보여줍니다. 이 갈림길 자체는 `shared.js`의
`recipeStepsOrLinkHtml()`로 뽑아 `recipe.js`(옛 `matchedDetailHtml`)와 같이 씁니다 —
두 화면이 같은 분기를 따로 들고 있던 것을 리뷰에서 걸러냈습니다. 냉장고 보유 여부
표시·"해먹었어요" 체크는 넣지 않았습니다 — 이 화면은 "뭘 즐겨찾기했는지 훑어보기"이지
조리 체크리스트가 아니기 때문입니다. 별을 누르면 `toggleFavorite()`이 저장소에서 빼고,
인덱스가 밀리는 문제를 피하려고 자리만 갈아끼우지 않고 목록·상세를 통째로 다시 그립니다
(선택 중이던 항목을 빼면 그 자리로 다음 항목이 자동으로 선택됩니다). 좁은 화면(640px
이하)에서는 왼쪽 목록이 위쪽 가로 스크롤 띠로 접히고 상세 카드가 그 아래 전체 폭을 씁니다.

**범위 밖**: 새 페이지(`favorites.html`)를 만들지 않았습니다. `mealplan.html`에 상시 노출
섹션을 두지 않았습니다(버튼+모달만). "자주 해먹은 순" 정렬은 하지 않았습니다(지금처럼 최근
즐겨찾기한 순 유지). 항목을 눌러서 특정 요일 칸에 바로 넣는 기능도 넣지 않았습니다 — 그건
지금 있는 "넣기 → 즐겨찾기에서 고르기" 흐름을 그대로 씁니다.

**테스트**: 프로덕션에서 Playwright로 버튼 클릭 → 모달 오픈(기본으로 첫 항목 선택) → 다른
항목 클릭 시 상세 전환 → 매칭 레시피/AI 레시피 두 갈림길 각각의 상세 렌더링 → 선택 중인
항목의 별 해제(목록·상세 모두 다음 항목으로 갱신, `localStorage`에도 반영) → 전부 뺀 뒤
빈 상태 문구까지 실측했습니다. 데스크톱 두 칸 레이아웃·모바일 스택형·다크 모드 모두
스크린샷으로 남겼습니다(`docs/qa-screenshots/mealplan-*-favorites-modal*.png`).

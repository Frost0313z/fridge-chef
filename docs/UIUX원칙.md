# UI/UX 원칙 — 냉털 셰프 (fridge-chef)

이 문서는 새로 정한 규칙이 아니라, **이미 코드에 반영돼 있는 판단들을 사후에 언어화한 것**입니다.
기능을 붙일 때마다 그때그때 내린 결정이 몇 가지 일관된 기준을 따르고 있었고, 그 기준을 적어두지 않으면
다음 기능에서 다르게 판단하게 되므로 정리했습니다.

원칙은 **세 개의 축**으로 나눕니다.

| 축 | 묻는 질문 | 실패하면 |
|---|---|---|
| [A. 안전](#a-안전-축--해를-끼치지-않는다) | 사용자에게 해를 끼치지 않는가 | 화면이 멈추고, 잘못된 정보를 주고, 원치 않는 일이 일어난다 |
| [B. 배려](#b-배려-축--실제로-돕는다) | 사용자를 실제로 돕는가 | 해는 없지만 아무도 쓰지 않는다 |
| [C. 디자인](#c-디자인-축--설명-없이-이해된다) | 화면이 스스로를 설명하는가 | 기능은 있는데 찾지 못하고, 눌러도 되는지 몰라 안 누른다 |

세 축은 별개입니다. A를 아무리 잘해도 B가 비면 "안전하게 쓸모없는" 서비스가 되고,
A·B가 있어도 C가 비면 그 가치가 화면에 전달되지 않습니다.

이 문서는 판을 거듭하며 축이 늘었습니다. 첫 판은 A축뿐이었고 — 원칙이 전부 "무엇이 잘못될 수 있는가"에서
출발한 개발자의 렌즈였습니다. 두 번째 판에서 B축을 분리했고, 세 번째 판에서 C축을 더했습니다.

[D. 체크리스트](#d-체크리스트)는 세 축 모두에서 아직 지키지 못한 항목이며, 그대로 다음 작업의 목록입니다.

# A. 안전 축 — 해를 끼치지 않는다

## A1. 애매하면 안전한 쪽으로 틀린다

> 판정이 불확실할 때는 **실패 비용이 싼 쪽으로** 틀리게 만든다.

장보기 리스트는 *식단 재료 − 재료함*으로 계산하는데, `"파"`와 `"파프리카"`처럼 이름이 겹치는 경우
보유 여부를 확실히 알 수 없습니다. 이때 두 방향의 오류는 비용이 전혀 다릅니다.

| 틀리는 방향 | 결과 | 비용 |
|---|---|---|
| 필요한 걸 안 사게 됨 | 그날 그 요리를 못 만듦 | **치명적** |
| 이미 있는 걸 또 사게 됨 | 돈이 조금 더 듦 | 감수 가능 |

그래서 `isCovered()`는 짧은 쪽이 1글자면 포함 매칭을 인정하지 않고, 애매한 항목을 리스트에 **남기는**
쪽으로 기웁니다.

> [!NOTE]
> 이 원칙에는 한계가 있습니다. 사용자 입장에서는 "또 사는 것"도 실패입니다.
> 추측의 방향을 고르는 대신 **한 번 물어보면** 두 실패를 모두 피할 수 있습니다 — [B8](#b8-애매하면-추측하지-말고-묻는다) 참고.
> A1은 묻지 않기로 했을 때의 차선책이지, 최선이 아닙니다.

**적용**: `js/mealplan.js` — `isCovered()`

<br>

같은 기준이 빈 재료함 처리에도 적용됩니다. 재료함이 비면 걸러낼 대상이 없어 식단의 모든 재료가
리스트에 담기는데, 이건 버그가 아니라 옳은 결과입니다(가진 게 없으면 다 사야 하니까).
그래서 제출을 막지 않고 **문구만** 사실에 맞춥니다 — 막으면 첫 방문자가 서비스를 아예 써볼 수 없습니다.

**적용**: `js/mealplan.js` — `renderShoppingList()`의 재료함 유무 분기

## A2. 실패해도 멈추지 않고, 원인별로 다르게 말한다

> 화면은 어떤 실패에서도 멈추지 않는다. 그리고 **사용자가 할 수 있는 행동**을 원인별로 다르게 안내한다.

| 상황 | 처리 | 이유 |
|---|---|---|
| 빈 입력 | 프론트에서 차단 (서버도 재검증) | API 호출 비용을 아낀다 |
| API 오류(4xx/5xx) | 서버가 502로 통일, 원인은 감춤 | 사용자가 OpenAI 내부 사정을 알 필요가 없다 |
| 응답 지연 | 서버 15초 · 클라이언트 20초(식단 25초) 이중 타임아웃 | 서버가 먼저 끊어도 클라이언트가 무한 대기하지 않는다 |
| 네트워크 단절 | `AbortError` 여부로 "지연"과 "연결 확인"을 구분 | 사용자가 취할 행동이 다르다 |

**적용**: `api/recommend.py` · `api/mealplan.py`의 예외 → HTTP 상태 매핑, `js/shared.js` — `postJson()`

### 사용자에게 보여줄 문구는 서버가 정한다

오류 응답의 스펙 자체에 이 규칙이 박혀 있습니다.

```python
응답(4xx/5xx): {"error": str, "message": str}  # message는 화면에 그대로 표시할 한국어 안내문
```

프론트는 `data.message`를 그대로 띄우고, 없을 때만 기본 문구로 대체합니다.

**적용**: `api/recommend.py` 상단 docstring, `js/shared.js` — `postJson()`

## A3. 자동화는 결제 직전에서 멈춘다

> 사용자 대신 **돈을 쓰는 행동**은 하지 않는다.

주간 식단의 장보기 리스트는 쿠팡 검색 링크만 제공하고 장바구니에 자동으로 담지 않습니다.
기술적 제약(개인이 쓸 수 있는 공식 장바구니 API가 없음)만이 아니라, 가능한 우회 방법(로그인 세션 자동화)이
이용약관 위반 소지가 있고 실제 결제로 이어질 수 있어서 범위를 의도적으로 제한했습니다.
이 제한은 숨기지 않고 화면과 FAQ 양쪽에 명시합니다.

**적용**: `js/mealplan.js` — `renderShoppingList()`, `about.html` FAQ

## A4. 되돌릴 수 없는 것에만 마찰을 넣는다

> 확인창은 일괄 적용하지 않는다. **복구 비용에 비례해서** 넣는다.

| 동작 | 확인창 | 이유 |
|---|---|---|
| 추천 이력 전체 지우기 | ✅ `confirm()` | 여러 건이 한 번에 사라지고 되돌릴 수 없다 |
| 식단 계획 지우기 | ✅ `confirm()` | AI 호출로 만든 결과가 통째로 사라진다 |
| 재료함 개별 삭제 (`×`) | ❌ 없음 | 하나 잘못 지워도 다시 입력하면 그만이다 |

**적용**: `js/recipe.js` — `initHistory()`, `js/mealplan.js` — 계획 지우기, `js/shared.js` — `initPantry()`

## A5. 저장하되 서버로 보내지 않는다

개인화를 계정·서버 DB 없이 `localStorage`만으로 구현합니다. 로그인 없는 서비스라는 구조를 유지하기 위한
선택이고, 대신 **무엇이 어디에 저장되고 어떻게 지우는지**를 FAQ에 명시합니다.

**적용**: `js/shared.js` — `loadJson`/`saveJson`, `about.html` FAQ

## A6. 입력은 관대하게, 출력은 엄격하게

> 사용자와 AI에게서 **받을 때는 최대한 받아주고**, 화면에 그리기 전에 엄격하게 정제한다.

| 방향 | 태도 | 구현 |
|---|---|---|
| 사용자 → 시스템 | 정확한 계량 불필요, 자유 텍스트, `계란 2개`·`두부(반모)` 아무 표기나 | `normalizeIngredient()` — 괄호·수량·단위 22종 제거 |
| AI → 시스템 | JSON 강제 후에도 **구조는 못 믿는다** | `sanitize_recipes()` / `sanitize_plan()` |
| 저장소 → 시스템 | 사용자가 직접 고쳤거나 옛 버전 값이 남아 있을 수 있다 | `loadJson()`의 fallback |
| 시스템 → 화면 | 무엇이 들어오든 이스케이프 | `escapeHtml()` — 재료명이 `aria-label` 속성값에도 들어가므로 따옴표까지 |

`response_format={"type": "json_object"}`는 **JSON이라는 것만** 보장하고 구조는 보장하지 않습니다.
"프론트는 서버 응답의 형식을 믿어도 된다"는 경계를 서버에 두어, 렌더링 코드마다 방어 코드를 흩뿌리지 않습니다.

**적용**: `api/*.py` — `to_str_list`/`sanitize_*`, `js/shared.js`, `js/mealplan.js`

## A7. 구조와 표현의 일관성

- **왼쪽 끝을 맞춘다** — `.page`는 헤더와 같은 폭(`--max-width: 1080px`), 글줄이 길면 읽기 어려운 요소만
  `max-width: 680px`로 좁히되 **`margin: auto`로 다시 가운데 정렬하지 않는다.** 그러면 헤더 로고와
  본문 제목의 왼쪽 시작선이 어긋납니다.
- **색은 토큰으로만 지정한다** — 다크 모드가 `:root[data-theme="dark"]`의 토큰 오버라이드로 동작하므로,
  하드코딩한 색은 그 요소만 테마를 따라가지 않습니다.
- **화면을 보지 못해도 흐름이 끊기지 않는다** — 본문 바로가기 링크, 로딩 `role="status"`,
  결과 `aria-live="polite"`, 오류 `role="alert"`, 닫힌 모바일 메뉴 `visibility: hidden`
  (`max-height: 0`만으로는 Tab 대상으로 남음), Esc 닫기 시 토글로 포커스 복귀,
  `:focus-visible` 전역 아웃라인, `prefers-reduced-motion` 존중.

**적용**: `css/style.css`

# B. 배려 축 — 실제로 돕는다

## 기준선은 배달앱이다

[기획서](./서비스기획서.md)는 이 서비스의 **진짜 경쟁 상대를 다른 레시피 서비스가 아니라 배달앱**으로 규정했습니다.
그렇다면 배려의 기준선도 배달앱입니다. 배달앱은 열자마자 선택지를 주고, 지난 주문을 버튼 하나로 반복하게 하고,
도착 시간을 분 단위로 알려주고, 결정한 뒤부터 음식이 도착할 때까지 사용자를 놓지 않습니다.

**"안전하지만 배달앱보다 불친절하면 사용자는 배달앱을 연다."** 이 축의 원칙은 전부 여기서 나옵니다.

## 이미 지키고 있는 것

먼저 공정하게 — 지금도 배려인 것들이 있습니다.

| 배려 | 어디에 |
|---|---|
| 정확한 계량을 요구하지 않음 | `about.html` FAQ, 프롬프트 |
| 소금·후추·기름·물은 없어도 있다고 쳐줌 | `api/recommend.py` — `SYSTEM_PROMPT` |
| 알려주지 않은 값비싼 재료를 임의로 추가하지 않음 | 같은 곳 |
| 자주 쓰는 재료를 매번 다시 타이핑하지 않게 함 | 재료함 (`js/shared.js`) |
| 인원수·상황을 **제출하지 않아도** 기억 | `js/recipe.js` — `change` 이벤트마다 저장 |
| 상황(자취/가족/다이어트)에 따라 추천 성격을 바꿈 | `SITUATION_HINTS` |
| 이력 클릭은 API를 다시 부르지 않아 즉시 뜸 | `js/recipe.js` — `initHistory()` |
| 장을 봐서 재료함을 채우면 저장된 계획의 살 것이 자동으로 줄어듦 | `js/mealplan.js` — 복원 시 재계산 |
| 오류·로딩 문구가 기계적이지 않음 | "🍳 재료를 살펴보고 요리를 고민하고 있어요..." |

**공통점**: 전부 **재료를 입력하기까지**의 배려입니다. 아래 원칙들은 그 이후가 비어 있다는 이야기입니다.

## B1. 빈 화면 앞에 세워두지 않는다

> 첫 화면에서 사용자가 "뭘 해야 하지"를 고민하게 만들지 않는다.

첫 방문자는 빈 재료함과 빈 입력란을 마주합니다. `placeholder`에 예시가 있지만 읽고, 이해하고,
자기 냉장고를 떠올려 타이핑해야 합니다. 배달앱은 열자마자 누를 수 있는 카드를 보여줍니다.

**현재**: ❌ 원클릭 예시 없음. `placeholder` 문자열만 (`recipe.html`)

## B2. 이미 알려준 것을 다시 기억하게 하지 않는다

> 서비스가 아는 정보를 사용자 머릿속에서 다시 꺼내게 하지 않는다.

가장 큰 모순입니다. 추천 카드의 재료 목록은 그냥 나열만 합니다 — 사용자는
`계란 2개 / 대파 / 두부 / 양파` 를 보고 **양파가 자기한테 있는지를 직접 기억해내야** 합니다.
재료함에 뭐가 있는지 서비스는 이미 알고 있는데도요.

주간 식단에서는 이 대조를 공들여 구현해놓고(`computeShoppingList`), 정작 레시피 추천에서는 하지 않습니다.
`isCovered()`가 이미 있으므로 새로 만들 것도 없습니다.

**현재**: ❌ 반쪽 — 주간 식단만 대조 (`js/mealplan.js`), 레시피 추천은 미대조 (`js/recipe.js` — `recipeCardHtml`)

## B3. 기다림에는 끝을 보여준다

> 얼마나 남았는지 모르는 기다림은 실제보다 길게 느껴진다.

서버 15초 + 클라이언트 20~25초입니다. 웹에서 20초는 매우 긴 시간이고, 배고픈 사람에게는 더 깁니다.
지금은 문구 한 줄만 떠 있고 경과 시간도, 예상 시간도, 취소 버튼도 없습니다.
사용자는 "멈춘 건가?"를 의심하면서 기다립니다.

**현재**: ❌ 정적 문구만 (`recipe.html` — `#loading`)

## B4. "이거 말고"를 쉽게 만든다

> 마음에 안 드는 건 정상이다. 그때 처음으로 되돌아가게 하지 않는다.

추천 3개가 다 안 당기면 폼까지 스크롤을 올려 같은 값으로 다시 제출해야 합니다.
재추천 버튼 하나가 없어서, 여기서 사용자는 그냥 배달앱을 엽니다.

**현재**: ❌ 없음

## B5. 결과는 부엌까지 따라간다

> 요리는 카드가 뜬 다음 20분 동안 벌어진다. 그 시간에도 곁에 있어야 한다.

지금 조리 순서는 정적인 `<ol>`입니다. 요리 중에는

- 손에 물이 묻은 채로 스크롤해야 하고
- 화면이 꺼지면 다시 켜서 위치를 찾아야 하고
- 지금 몇 번째인지 표시할 방법이 없습니다

"냉장고를 여는 순간 요리가 시작됩니다"라고 써놓고, 정작 요리하는 동안은 아무것도 하지 않습니다.

**현재**: ❌ 없음 (`js/recipe.js` — `recipeCardHtml`의 `<ol>`)

## B6. 좋았던 것은 붙잡을 수 있게 한다

> 재방문을 전제로 설계했다면, 좋았던 경험이 남아야 재방문할 이유가 생긴다.

이력은 최근 5개가 자동으로 밀려 나갑니다. "이거 맛있었어"를 표시할 방법이 없어서,
지난주에 성공한 요리는 여섯 번만 추천받으면 사라집니다.
배달앱의 재주문 버튼에 해당하는 기능이 없는 셈입니다.

**현재**: ❌ 고정·즐겨찾기 없음 (`js/recipe.js` — `HISTORY_LIMIT = 5`, 오래된 것부터 삭제)

## B7. 막다른 길을 만들지 않는다

> 어떤 화면에서도 사용자가 다음에 할 수 있는 일이 하나는 있어야 한다.

오류 문구가 "잠시 후 다시 시도해주세요"로 끝납니다. 지금 저녁을 정해야 하는 사람에게 할 말이 아닙니다.
브라우저에 최근 추천 이력이 이미 저장돼 있는데도 그쪽으로 안내하지 않습니다.
[A2](#a2-실패해도-멈추지-않고-원인별로-다르게-말한다)는 "원인을 정확히 알린다"까지 하고 멈췄습니다. 배려는 그다음, **대안을 주는 것**입니다.

**현재**: ❌ 대안 제시 없음 (`js/recipe.js` — `status.showError()` 호출만)

## B8. 애매하면 추측하지 말고 묻는다

> 추측의 방향을 고르기 전에, 물어볼 수 있는지 먼저 확인한다.

[A1](#a1-애매하면-안전한-쪽으로-틀린다)은 `재료함: 대파` + `식단: 파`에서 "또 사는" 쪽으로 틀리기를 택했습니다.
안전한 선택이지만, 사용자에게는 **두 방향 모두 실패**입니다. 애매한 항목은 보통 한두 개뿐이므로,
장보기 리스트 위에 "대파, 갖고 계신가요?"를 한 번 묻는 것이 양쪽을 다 피하는 길입니다.

**현재**: ❌ 묻지 않고 추측 (`js/mealplan.js` — `isCovered()`)

# C. 디자인 축 — 설명 없이 이해된다

A·B가 "무엇을 할 것인가"라면 C는 "그것이 화면에서 어떻게 보이는가"입니다.
아래 10개는 일반적인 UI 디자인 기준을 이 서비스에 적용한 것이고,
각 항목의 판정(✅ 지킴 / ⚠️ 부분 / ❌ 어긋남)은 현재 코드를 검토한 결과입니다.

## C1. 개발자가 아닌 사용자 측면에서 만든다 ⚠️

> 사용자가 알 필요 없는 것을 화면에 두지 않는다.

- `about.html`의 **기술 스택 섹션**이 소개 페이지 4개 섹션 중 하나를 차지합니다. "Vercel Serverless
  Functions (Python)", "OpenAI API (Chat Completions)" — 저녁 메뉴를 정하러 온 사람에게는 의미 없는
  정보이고, 미션 평가자를 위한 것입니다. README에 이미 있습니다.
- 오류 문구 3개가 시스템의 언어입니다 — "요청 형식이 올바르지 않아요"(이해도 조치도 불가),
  "서버에 API 키가 설정되어 있지 않아요"(사용자 잘못이 아닌데 사용자에게 말함), "AI 응답을
  해석하지 못했어요"("해석"이 기술 용어).

## C2. 각 화면은 한 가지 행동에 집중하게 한다 ❌

> 한 화면에서 사용자가 해야 할 일은 하나여야 한다.

**가장 크게 어긋난 원칙입니다.** `recipe.html`은 한 스크롤에 섹션이 4개이고, 주 행동이 한가운데 있습니다.

```
① 내 재료함        ← 등록하기
② 추천 폼          ← 추천받기   ★ 진짜 주 행동
③ 결과
④ 최근 추천 이력   ← 지난 것 보기
```

재료함이 폼보다 **위**에 있어서, 오늘 한 번만 써볼 사람도 "재료를 등록하라"는 요구를 먼저 마주합니다.
`mealplan.html`도 같은 구조입니다.

> [!NOTE]
> 홈의 CTA 2개(레시피 추천 · 주간 식단)도 이 원칙과 긴장 관계입니다.
> primary/secondary 위계로 "주 행동 하나 + 대안 하나"를 유지했지만, 엄밀히는 한 가지 행동이 아닙니다.
> [B1](#b1-빈-화면-앞에-세워두지-않는다)·발견성과의 맞교환으로 받아들인 것이며, 셋 이상으로 늘리지 않습니다.

## C3. 반응을 보여준다 ⚠️

> 사용자의 모든 조작에는 눈에 보이는 반응이 따라야 한다.

**어긋난 곳** — 재료함에서 **이미 있는 재료를 다시 추가하면 아무 일도 일어나지 않습니다.**
`initPantry()`의 `addItems()`가 중복이면 `changed = false`로 렌더도 하지 않고 조용히 끝나서,
입력창만 비워집니다. 사용자는 버튼을 눌렀는데 화면이 그대로라 고장으로 인식합니다.
빈 값으로 "추가"를 눌러도 마찬가지입니다.

또한 **결과가 도착해도 그 위치로 스크롤하지 않습니다.** 이력 클릭에는 `scrollIntoView`가 있는데
(`js/recipe.js`), 정작 20초를 기다린 AI 결과에는 없습니다.

**지킨 것**: 제출 중 버튼 `disabled`, 로딩 문구, hover 반응, 다크 모드 즉시 반영, 이력 클릭 시 스크롤.

## C4. 맥락 있는 흐름을 만든다 ❌

> 한 행동이 끝나면 다음에 할 수 있는 일이 보여야 한다.

- 추천 카드가 뜨면 **흐름이 끝납니다.** 다음 행동 제안이 없습니다.
- `about.html` 이용 방법 3단계를 다 읽어도 **"지금 해보기" 버튼이 없어** 네비게이션으로 돌아가야 합니다.
- 장보기 리스트에서 쿠팡으로 나간 뒤 **돌아올 지점이 없습니다.** "장 봤어요 → 재료함에 반영" 같은
  복귀 경로가 없어서 사용자가 재료함에 수동으로 다시 입력해야 하고, 여기서 흐름이 끊깁니다.
- 레시피 추천과 주간 식단을 오가는 유도가 홈에만 있습니다.

## C5. 시각적 일관성을 유지한다 ⚠️

> 같은 의미는 같은 모양으로 보여야 한다.

현재 값 분포를 세어보면 규칙이 아니라 그때그때 정한 값들입니다.

```
border-radius:  10px×7 · var(--radius)×3 · 50%×3 · 999px×2 · 12px · 4px · 2px      → 7종
font-size:      0.8 / 0.85 / 0.88 / 0.9 / 0.92 / 0.95 / 1 / 1.05 / 1.1 / 1.15 / 1.2 / 1.8rem  → 12종
```

`--radius: 14px` 토큰이 있는데 하드코딩 `10px`가 7곳으로 더 많습니다. 0.88·0.9·0.92rem이 공존하는 건
의도한 위계가 아닙니다. spacing 토큰은 아예 없습니다.

- **같은 위계의 `h2`가 두 크기** — `.page h2` 1.2rem vs `.pantry h2`·`.shopping-list-section h2`·`.history-header h2` 1.1rem
- **카드 padding 제각각** — feature-card `28px 22px`, recipe-card `20px`, mealplan-day-card `18px`
- **다크 모드가 깨지는 곳** — `css/style.css`의 `.error-message { border: 1px solid #f4c2c2 }`가
  전체에서 유일하게 토큰을 쓰지 않은 색입니다. 다크 배경(`--color-danger-bg: #3a2323`) 위에
  밝은 분홍 테두리가 그대로 떠서 그 요소만 테마를 따라가지 않습니다.
  [A7](#a7-구조와-표현의-일관성)에 "색은 토큰으로만"이라 써놓고 어긴 지점입니다.
- **죽은 코드** — `.required` 클래스가 CSS에 있으나 HTML 4개 어디에도 없습니다.

## C6. 예상할 수 있어야 한다 ⚠️

> 누르기 전에 무슨 일이 일어날지 알 수 있어야 한다.

- **위계 붕괴** — 재료함의 "추가" 버튼이 주 CTA와 같은 `--color-primary` 채움입니다.
  화면에서 가장 눈에 띄어야 할 "AI에게 추천받기"와 시각적 무게가 같고, 위에 있어서 먼저 보입니다.
- `.mealplan-clear-btn`이 `hidden` 해제와 함께 제출 버튼 아래에 **예고 없이 나타납니다.**
- 이력 항목이 `<button>`인데 카드처럼 생겨서, 누르면 결과 영역이 바뀐다는 걸 예측하기 어렵습니다.

## C7. 의미 있는 움직임만 보여준다 ✅

> 움직임은 장식이 아니라 상태 변화를 알리는 수단이다.

**대체로 지켰습니다.** 전체 transition이 3개(body 색 `0.15s`, 버튼 `0.15s`, 메뉴 `0.2s`)뿐이고,
`@keyframes` 애니메이션은 0개이며, `prefers-reduced-motion`에서 전부 제거됩니다.

다만 **움직임의 배치가 반대입니다.**

| 위치 | 현재 | 문제 |
|---|---|---|
| `.cta-button:hover` | `translateY(-1px)` | 1px는 인지되지 않는다. 장식에 가깝다 |
| 결과 카드 등장 | 전환 없음 | AI가 20초 걸려 만든 결과가 툭 나타난다. 움직임이 의미 있는 유일한 지점인데 비어 있다 |

## C8. 누구나 이해하기 쉬운 글을 제공한다 ⚠️

> 읽고 나서 무엇을 해야 할지 알 수 있어야 한다.

**지킨 것**: 전체 "~해요"체 통일, "재료를 1개 이상 입력해주세요",
"재료함만으로 충분해요! 따로 살 재료가 없어요 🎉".

**어긋난 곳**: [C1](#c1-개발자가-아닌-사용자-측면에서-만든다-)의 오류 문구 3개와 기술 스택 섹션.
그리고 홈 첫 화면에서 **"냉털"을 설명 없이 브랜드로 씁니다** — 뜻풀이는 `about.html`에만 있습니다.

## C9. 사용자의 익숙함을 존중한다 ⚠️

> 이미 아는 방식대로 동작해야 한다. 새 관례를 발명하지 않는다.

**지킨 것**: `<select>` 기본 스타일 유지, `×` 삭제, 우측 상단 "전체 지우기",
외부 링크 새 탭 + `rel="noopener noreferrer"`.

**어긋난 곳 — 모바일 관례**

| 항목 | 현재 | 관례 |
|---|---|---|
| `.pantry-chip-remove` 터치 타겟 | **20×20px** | 최소 44×44px |
| 모바일 제출 버튼 | `align-self: flex-start`로 좁게 왼쪽 정렬, 640px 미디어 쿼리에 full-width 규칙 없음 | 모바일 폼 버튼은 full-width |

## C10. 필요한 만큼만 단순하게 디자인한다 ⚠️

> 요소를 늘리기 전에 뺄 수 있는지 먼저 본다.

**지킨 것**: 프레임워크 없이 872줄, 빌드 도구 없음 — 페이지 4개 규모에 적절합니다.

**어긋난 곳**: **이모지가 12종 이상**입니다(🧊 🥕 🤖 🛒 📖 🕘 🗓️ ⏱ 🍳 🎉 💼 ✉️).
톤은 살지만 전부 강조되면 아무것도 강조되지 않습니다 — 결과 카드의 `⏱`와 섹션 제목의 `🥕`가
같은 비중으로 보입니다. 사용 자리를 정해야 합니다(예: 섹션 제목에만).

토큰 체계도 절반만 있습니다 — `--radius`·`--header-height`는 있는데 spacing·font-size 스케일이 없어
하드코딩이 난립합니다([C5](#c5-시각적-일관성을-유지한다-)).

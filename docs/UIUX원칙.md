## 1. 애매하면 안전한 쪽으로 틀린다

> 판정이 불확실할 때는 **실패 비용이 싼 쪽으로** 틀리게 만든다.

장보기 리스트는 *식단 재료 − 재료함*으로 계산하는데, `"파"`와 `"파프리카"`처럼 이름이 겹치는 경우
보유 여부를 확실히 알 수 없습니다. 이때 두 방향의 오류는 비용이 전혀 다릅니다.

| 틀리는 방향 | 결과 | 비용 |
|---|---|---|
| 필요한 걸 안 사게 됨 | 그날 그 요리를 못 만듦 | **치명적** |
| 이미 있는 걸 또 사게 됨 | 돈이 조금 더 듦 | 감수 가능 |

그래서 `isCovered()`는 짧은 쪽이 1글자면 포함 매칭을 인정하지 않고, 애매한 항목을 리스트에 **남기는**
쪽으로 기웁니다. `재료함: 대파` + `식단: 파`는 여전히 "있는 걸 또 사는" 쪽으로 틀리지만 의도한 선택입니다.

**적용**: `js/mealplan.js` — `isCovered()`

<br>

같은 기준이 빈 재료함 처리에도 적용됩니다. 재료함이 비면 걸러낼 대상이 없어 식단의 모든 재료가
리스트에 담기는데, 이건 버그가 아니라 옳은 결과입니다(가진 게 없으면 다 사야 하니까).
그래서 제출을 막지 않고 **문구만** 사실에 맞춥니다 — 막으면 첫 방문자가 서비스를 아예 써볼 수 없습니다.

**적용**: `js/mealplan.js` — `renderShoppingList()`의 재료함 유무 분기

## 2. 실패해도 멈추지 않고, 원인별로 다르게 말한다

> 화면은 어떤 실패에서도 멈추지 않는다. 그리고 **사용자가 할 수 있는 행동**을 원인별로 다르게 안내한다.

미션 요구사항은 실패 처리 1개 이상이지만, 실제로 발생 가능한 실패는 성격이 다르므로 나눴습니다.

| 상황 | 처리 | 이유 |
|---|---|---|
| 빈 입력 | 프론트에서 차단 (서버도 재검증) | API 호출 비용을 아낀다 |
| API 오류(4xx/5xx) | 서버가 502로 통일, 원인은 감춤 | 사용자가 OpenAI 내부 사정을 알 필요가 없다 |
| 응답 지연 | 서버 15초 · 클라이언트 20초(식단 25초) 이중 타임아웃 | 서버가 먼저 끊어도 클라이언트가 무한 대기하지 않는다 |
| 네트워크 단절 | `AbortError` 여부로 "지연"과 "연결 확인"을 구분 | 사용자가 취할 행동이 다르다 |

**적용**: `api/recommend.py` · `api/mealplan.py`의 예외 → HTTP 상태 매핑, `js/shared.js` — `postJson()`

### 사용자에게 보여줄 문구는 서버가 정한다

오류 응답의 스펙 자체에 이 규칙이 박혀 있습니다.

```python
응답(4xx/5xx): {"error": str, "message": str}  # message는 화면에 그대로 표시할 한국어 안내문
```

프론트는 `data.message`를 그대로 띄우고, 없을 때만 기본 문구로 대체합니다. 오류 문구를 프론트 곳곳에
흩뿌리지 않고 서버 한 곳에 모아두기 위한 경계입니다.

**적용**: `api/recommend.py` 상단 docstring, `js/shared.js` — `postJson()`의 반환값

## 3. 자동화는 결제 직전에서 멈춘다

> 사용자 대신 **돈을 쓰는 행동**은 하지 않는다.

주간 식단의 장보기 리스트는 쿠팡 검색 링크만 제공하고 장바구니에 자동으로 담지 않습니다.
기술적 제약(개인이 쓸 수 있는 공식 장바구니 API가 없음)만이 아니라, 가능한 우회 방법(로그인 세션 자동화)이
이용약관 위반 소지가 있고 실제 결제로 이어질 수 있는 자동화라서 범위를 의도적으로 제한했습니다.

이 제한은 숨기지 않고 화면과 FAQ 양쪽에 명시합니다 — "자동으로 담기지는 않고, 클릭하면 쿠팡 검색 결과가
새 탭에서 열려요."

**적용**: `js/mealplan.js` — `renderShoppingList()`의 검색 링크, `about.html` FAQ

## 4. 되돌릴 수 없는 것에만 마찰을 넣는다

> 확인창은 일괄 적용하지 않는다. **복구 비용에 비례해서** 넣는다.

| 동작 | 확인창 | 이유 |
|---|---|---|
| 추천 이력 전체 지우기 | ✅ `confirm()` | 여러 건이 한 번에 사라지고 되돌릴 수 없다 |
| 식단 계획 지우기 | ✅ `confirm()` | AI 호출로 만든 결과가 통째로 사라진다 |
| 재료함 개별 삭제 (`×`) | ❌ 없음 | 하나 잘못 지워도 다시 입력하면 그만이다 |

**적용**: `js/recipe.js` — `initHistory()`, `js/mealplan.js` — 계획 지우기 핸들러, `js/shared.js` — `initPantry()`

## 5. 반복 입력은 기억하되 서버로 보내지 않는다

> 이 서비스는 하루 1~2끼마다 반복 사용되는 것을 전제한다. 두 번째 방문의 조작량이 첫 방문과 같으면 실패다.

재방문 시 복원되는 값은 7가지입니다.

| 키 | 내용 | 범위 |
|---|---|---|
| `fridge-chef-theme` | 다크/라이트 | 전 페이지 |
| `fridge-chef-pantry` | 내 재료함 | 두 AI 페이지 공유 |
| `fridge-chef-prefs` | 인원수·상황 | 두 AI 페이지 공유 |
| `fridge-chef-history` | 최근 추천 5개 | 레시피 추천 |
| `fridge-chef-recipe-timelimit` | 조리 시간 | 레시피 추천 전용 |
| `fridge-chef-mealplan` | 식단 계획 | 주간 식단 |
| `fridge-chef-mealplan-days` | 계획 일수 | 주간 식단 전용 |

세부 규칙:

- **제출하지 않아도 기억한다** — 인원수·상황은 `change` 이벤트마다 즉시 저장됩니다. 폼을 채우다 이탈해도 남습니다.
- **두 페이지가 같은 값을 쓴다** — 인원수·상황·재료함은 공유하고, 조리 시간·일수처럼 한쪽에서만 의미 있는 값은 전용 키로 둡니다.
- **이미 받은 결과는 다시 요청하지 않는다** — 이력 클릭은 저장된 객체로 카드를 다시 그릴 뿐 API를 호출하지 않습니다. 저장된 식단도 재방문 시 그대로 복원됩니다.
- **저장된 계획의 장보기 리스트는 매번 다시 계산한다** — 계획은 그대로 두되 리스트는 *그 시점의* 재료함 기준으로 재계산합니다. 장을 봐서 재료함을 채우면 같은 계획인데도 살 것이 줄어듭니다.

### 저장은 하되 서버로 보내지 않는다

위 개인화를 계정·서버 DB 없이 `localStorage`만으로 구현합니다. 로그인 없는 서비스라는 구조를 그대로
유지하기 위한 선택이고, 대신 **무엇이 어디에 저장되고 어떻게 지우는지**를 FAQ에 명시합니다.

**적용**: `js/shared.js` — `loadJson`/`saveJson`/`loadPrefs`/`savePrefs`, `about.html` FAQ

## 6. 입력은 관대하게, 출력은 엄격하게

> 사용자와 AI에게서 **받을 때는 최대한 받아주고**, 화면에 그리기 전에 엄격하게 정제한다.

| 방향 | 태도 | 구현 |
|---|---|---|
| 사용자 → 시스템 | 정확한 계량 불필요, 자유 텍스트, 쉼표로 여러 개, `계란 2개`·`두부(반모)` 아무 표기나 | `normalizeIngredient()`가 괄호·수량·단위 22종을 걷어냄 |
| AI → 시스템 | JSON 강제(`response_format`) 후에도 **구조는 못 믿는다** | `sanitize_recipes()` / `sanitize_plan()`이 타입·개수를 강제 |
| 저장소 → 시스템 | 사용자가 직접 고쳤거나 옛 버전 값이 남아 있을 수 있다 | `loadJson()`이 파싱 예외·타입 불일치 시 fallback 반환 |
| 시스템 → 화면 | 무엇이 들어오든 이스케이프 | `escapeHtml()`이 `& < > " '` 5종 치환 (재료명이 `aria-label` 속성값에도 들어가므로 따옴표까지) |

`response_format={"type": "json_object"}`는 **JSON이라는 것만** 보장하고 그 안의 구조는 보장하지 않습니다.
"프론트는 서버 응답의 형식을 믿어도 된다"는 경계를 서버 쪽에 두어, 렌더링 코드마다 방어 코드를
흩뿌리지 않게 했습니다.

**적용**: `api/*.py` — `to_str_list`/`sanitize_*`, `js/shared.js` — `loadJson`/`escapeHtml`, `js/mealplan.js` — `normalizeIngredient`

## 7. 말투와 표현

### 톤
- 전부 **"~해요"체**. 오류 문구도 예외가 아닙니다 — "AI 응답이 지연되고 있어요. 잠시 후 다시 시도해주세요."
- 로딩 문구는 기계적으로 쓰지 않습니다 — "🍳 재료를 살펴보고 요리를 고민하고 있어요...", "🗓️ 일주일치 식단을 짜고 있어요..."
- 섹션 제목마다 이모지 1개로 구역을 표시합니다 (🥕 내 재료함 · 🕘 최근 추천 받은 요리 · 🛒 장보기 리스트)

### 빈 상태에는 다음 행동을 적는다
비어 있는 영역을 그냥 비워두지 않고, 무엇을 하면 채워지는지 적습니다 —
"아직 등록된 재료가 없어요. 위에 입력해서 추가해보세요."

### 화면을 보지 못해도 흐름이 끊기지 않는다
"재료 입력 → 추천 확인"이라는 핵심 흐름을 키보드와 스크린리더만으로 끝까지 갈 수 있는지를 기준으로 잡았습니다.

| 항목 | 처리 |
|---|---|
| 키보드 진입 | `본문 바로가기` 링크 — 평소 화면 밖, Tab 포커스 시 노출 |
| AI 진행 | 로딩에 `role="status"` + `aria-live="polite"` |
| AI 결과 | 결과 영역에 `aria-live="polite"` |
| 오류 | `role="alert"` — 즉시 읽힘 |
| 모바일 메뉴 | 닫힌 상태에서 `visibility: hidden` — `max-height: 0`만으로는 링크가 Tab 이동 대상으로 남는다 |
| 메뉴 닫기 | 햄버거 재클릭 외에 Esc 키·바깥 클릭, Esc로 닫으면 토글 버튼으로 포커스 복귀 |
| 초점 표시 | `:focus-visible` 전역 아웃라인 (마우스 클릭 시에는 표시하지 않음) |
| 모션 | `prefers-reduced-motion` 존중 |

### 왼쪽 끝을 맞춘다
`.page` 전체는 헤더와 같은 폭(`--max-width: 1080px`)으로 두고, 글줄이 길면 읽기 어려운 요소(문단·폼·입력줄)만
`max-width: 680px`로 좁힙니다. **좁힌 뒤 `margin: auto`로 다시 가운데 정렬하지 않는 것이 핵심**입니다 —
그러면 헤더 로고와 본문 제목의 왼쪽 시작선이 어긋납니다. 반대로 결과 카드 그리드는 폭을 넓게 둬서
화면이 넓을 때 열 수가 자연스럽게 늘어나게 합니다.

### 색은 토큰으로만 지정한다
다크 모드가 `:root[data-theme="dark"]`의 토큰 오버라이드로 동작하므로, 색을 하드코딩하면 그 요소만
테마를 따라가지 않습니다. 새 컴포넌트도 `--color-surface` / `--color-border` / `--color-primary` 등
기존 토큰만 사용합니다.

**적용**: `css/style.css` — `:root` 토큰 정의, `.page` 및 폭 제한 규칙, `:focus-visible`, 640px 미디어 쿼리

## 8. 아직 지키지 못한 곳

위 원칙과 현재 코드가 어긋나 있는 지점입니다. 다음 작업의 체크리스트로 씁니다.

| # | 어긋난 곳 | 어떤 원칙과 충돌하나 |
|---|---|---|
| 1 | `about.html`의 이용 방법 3단계가 레시피 추천 흐름만 설명하고 주간 식단이 등장하지 않음 | 홈은 두 기능을 대등하게 노출하도록 고쳤는데 소개 페이지는 그대로라, 같은 문제가 한 페이지 옮겨간 상태 |
| 2 | 재료함 설명이 두 페이지에서 다름 — `recipe.html`은 "다시 입력할 필요 없다"만, 장보기 리스트에서 걸러진다는 정보는 `mealplan.html`에만 있음 | 같은 데이터인데 페이지마다 다른 가치를 설명 |
| 3 | 추천 이력에 개별 삭제가 없고 "전체 지우기"만 있음 (재료함은 개별 `×` 제공) | [4번](#4-되돌릴-수-없는-것에만-마찰을-넣는다)의 대칭이 깨짐 — 하나만 지우려면 전부 지워야 함 |
| 4 | 결과 영역(`#result`)에만 빈 상태 안내가 없음 (재료함·이력에는 있음) | [7번](#7-말투와-표현) "빈 상태에는 다음 행동을 적는다" |
| 5 | 배포 URL과 실행 화면 스크린샷이 README에 비어 있음 | 배포 완료 후 채울 것 |

# 스펙 — 사진으로 재료 등록 (영수증 촬영 / 쿠팡 구매내역 캡처)

**상태**: 백엔드 프로토타입 구현 완료 (2026-08-20, `api/pantry_import.py`) — 진입 UI(§0)·확인
화면(§4)은 아직 없음. 실측 샘플 3장(쿠팡 1, 빵집 영수증 1, 마트 영수증 1) 기반
**관련 논의**: pantry 수동 입력의 마찰 비용 → 사진 인식으로 자동 등록 제안 → 소규모 실측(쿠팡 캡처 1장, 빵집 영수증 1장, 마트 영수증 1장)

---

## 배경

`pantry.html`은 지금 순수 텍스트 입력(`#pantry-input`)으로 재료를 한 줄씩 넣는다. 재료가 많아지면
하나하나 타이핑하는 게 피곤하다는 문제 제기가 있었고, 이미 쓰고 있는 `gpt-4o-mini`가 이미지(비전)
입력을 받는다는 점에서 "사진 한 장으로 재료를 등록"하는 방향을 검토했다. 후보는 두 가지 —
(1) 쿠팡 등 온라인 장보기 구매내역 캡처, (2) 마트·편의점 영수증 촬영.

작게 실측(쿠팡 캡처 1장, 빵집 영수증 1장)해본 결과, 이 기능의 핵심 난이도는 "글자를 읽는 것"(OCR)이
아니라 **"읽은 상품명을 재료로 쓸지 말지, 어떻게 정규화할지 판단하는 것"**으로 드러났다. 아래 스펙은
이 실측을 바탕으로 정리한다.

## 실측 결과 (샘플 3장 — 육안 확인, 실제 API 파이프라인은 아직 없음)

### 쿠팡 구매내역 캡처 1장

주문 3건(닭가슴살 볼 냉동 믹스세트, 우유, 계란)을 텍스트로 읽는 것 자체는 문제없었다 — 디지털
텍스트라 왜곡이 없고, 상품명·가격·버튼(배송조회, 리뷰작성하기 등)이 레이아웃상 뚜렷이 분리돼 있어
걸러내기 쉬웠다.

다만 "로켓프레시 한끼통살 닭가슴살 볼 5종 x 2개 믹스세트(냉동)"처럼 가공식품·완제품이 섞여 있었다.
이런 상품을 원문 그대로("닭가슴살 볼") 남기면, 레시피 코퍼스(홈쿠킹 재료명만 있음, `spec-recipe-match.md`
참고)에 대응하는 이름이 없어 매칭이 아예 안 걸린다. **원재료명으로 정규화하는 쪽으로 결정했다**
(아래 핵심 원칙 1).

### 마트·편의점 영수증 1장 (대체: 빵집 영수증)

장보기 영수증이 없어 빵집(성심당) 영수증으로 대체 테스트했다. 사진이 기울어져 있었지만 텍스트는
또렷하게 읽혔다("순수마들렌(날개) 1,300원") — 촬영 방식이라도 글자 인식 자체가 크게 어렵진 않아
보인다.

다만 이 영수증의 유일한 품목("마들렌")은 조리 재료가 아니라 완제품 간식이었다. 이건 쿠팡 테스트보다
한 단계 더 까다로운 필터링 문제를 드러냈다 — **"음식이지만 요리 재료가 아닌 것"**을 걸러야 한다.

### 마트 영수증 1장 (실측 3차, 2026-08-20 — 제이식자재마트)

드디어 이 기능이 실제로 노리던 유형의 표본을 확인했다. 7개 품목, 바코드 번호·단가·수량·금액이
품목명과 같이 찍혀 있는 전형적인 마트 영수증이다.

| 품명(원문) | 요리 재료인가 | 추출 판단 |
|---|---|---|
| 프리미엄소주오크젠360ml | 애매(음료지만 조리에도 씀) | "소주"로 추출 — 아래 참고, 실제로 자주 쓰이는 재료다 |
| 롯데 도리토스나쵸치즈맛 | 아니오(과자) | 걸러야 함 |
| 롯데 알뜨소세지150g | 예 | "소세지"로 추출 |
| 동서)미니단백질바21*16 | 아니오(간식) | 걸러야 함 |
| 안심유부산국탕용320 | 예 | ~~"유부"로 추출~~ → **오독 확인됨(2026-08-20)**: 실제로는 어묵탕 재료(어묵). 아래 참고 |
| 동원)저스트노슈가스위트콘340g | 예 | "스위트콘"(또는 "옥수수")으로 추출 |
| 오뚜기 3분카레약간매운맛200g | 애매(즉석조리식품) | "카레"로 추출 — 닭가슴살볼과 같은 성격의 부정확함 |

걱정했던 것과 달리 "성)계란1" 같은 매장 내부 축약 코드는 안 보였다. 브랜드 접두어("롯데",
"동서)", "동원)")가 상품명에 공백 없이 붙어 있어 읽기 번거롭긴 해도, 핵심 재료 단어("소세지",
"유부", "스위트콘")는 그 안에서 골라낼 수 있었다. 바코드 숫자·단가·수량·금액이 같이 찍혀 있어도
품명 줄과 뚜렷이 구분됐다 — §구현 전 확인 사항 3(숫자 오작동)의 우려는 이번 표본에선 현실화되지
않았다.

**다만 진짜 재료로 쓸 만한 건 7개 중 3개뿐이었다**(소세지·유부·스위트콘). 나머지는 과자·간식처럼
아예 재료가 아니거나(2개), 소주·3분카레처럼 판단이 갈리는 항목(2개)이다. 실제 장바구니를 그대로
넣으면 재료 인식률이 절반에 못 미칠 수 있다는 뜻이라, 이 기능의 체감 효용을 과대평가하지 않아야
한다.

#### 핵심 원칙 3(어휘 대조 필터)이 놓칠 뻔한 사례를 직접 확인했다

"과자·간식은 재료 어휘에 없어서 자동으로 걸러진다"는 가정(핵심 원칙 3)을 이번 표본으로 실제
코퍼스에 대고 확인해봤다(4개 CSV, 234,538개 레시피, `\x07` 구분자로 파싱).

| 검색어 | 정확히 일치하는 재료명 등장 횟수 |
|---|---|
| 소주 | 735회 |
| 소세지 | 179회 |
| 유부 | 99회 |
| 스위트콘 | 76회 |
| 카레(관련어 포함) | 39~404회 |
| **도리토스** | **1회** |
| **단백질바** | **0회**(부분 일치 2회) |

**"도리토스"가 정확히 1회 등장한다** — 어느 레시피가 나쵸 토핑으로 썼기 때문이다. 이 어휘가
234,538개 레시피 전체에서 뽑힌, 사람들이 자유롭게 적어 넣은 원문이라 이런 예외가 섞여 있다.
그러니 "어휘에 있으면 재료다"라는 지금 규칙 그대로는 "도리토스"가 걸러지지 않고 살아남는다 —
핵심 원칙 3이 완벽하지 않다는 뜻이다.

**보완**: 어휘 대조에 최소 등장 횟수 기준을 추가한다. 1~2회짜리 우연한 매치는 재료로 안 치고,
일정 횟수 이상(예: 5회) 등장해야 "진짜 자주 쓰이는 재료"로 인정한다. 정확한 문턱값은
`spec-recipe-match.md`의 `MIN_COVERAGE`처럼 실측 후 조정 대상이다 — 이번 표본 기준으로는 5만
넘어도 소세지(179)·유부(99)·스위트콘(76)·소주(735)는 다 남고 도리토스(1)·단백질바(0~2)는
걸러진다.

> [!NOTE]
> "소주"가 735회로 꽤 자주 등장하는 건 우연이 아니다 — 생선 비린내를 없애거나 고기를 재울 때
> 실제로 흔히 쓰는 재료라, 걸러지지 않는 게 맞다. 음료냐 아니냐로 미리 판단하지 않고 어휘
> 빈도에 맡긴 게 오히려 옳은 결과를 냈다.

#### 두 가지 오류는 종류가 다르다 — 하나는 코드로 막고, 하나는 못 막는다

이 문서를 쓰다가 직접 겪었다. "안심유부산국탕용320"을 "유부"로 추출·표기했는데, 실제로는
어묵탕 재료(어묵)였다. 대전 자취생 당사자가 실물을 보고서야 잡아낸 오류다.

이건 위에서 다룬 "도리토스"·"마들렌" 문제와 겉보기엔 비슷해 보이지만 원인이 다르다.

| | "재료가 아닌 걸 재료로 인식" (도리토스·마들렌) | "재료인 건 맞는데 다른 재료로 오독" (유부↔어묵) |
|---|---|---|
| 원인 | 애초에 재료 어휘에 없거나(마들렌) 우연히 1회만 등장(도리토스) | 브랜드 상품명·축약 표기 때문에 비슷한 다른 재료로 잘못 해석 |
| 코드로 막을 수 있나 | **된다** — 어휘 대조 + 최소 등장 횟수 문턱값(핵심 원칙 3) | **안 된다** — "유부"도 "어묵"도 둘 다 어휘에 흔히 등장하는 진짜 재료라, 대조를 통과해버린다 |
| 막는 방법 | 코드(자동) | **사용자 확인(핵심 원칙 4)뿐 — 그 외엔 없다** |

즉 핵심 원칙 3(어휘 대조)은 "이게 재료냐 아니냐"를 판단하는 데는 도움이 되지만, "이게 정확히
무슨 재료냐"를 검증해주지는 못한다. 이번 실수가 그 한계를 정확히 보여준 사례라, **§4 확인
화면은 있어도 되는 부가 기능이 아니라 이 기능의 정확성을 보장하는 유일한 최종 관문**이라는
점을 핵심 원칙 4에 명시적으로 못 박는다.

## 핵심 원칙

1. **원재료명으로 정규화한다.** 가공식품·브랜드 상품명을 그대로 남기지 않는다. 이 부정확함은 새로
   생기는 문제가 아니라, 지금 텍스트 수동 입력에도 이미 있던 것과 같은 수준이다(사용자가 "닭가슴살"이라
   입력해도 앱은 생닭인지 가공육인지 구분 못 한다) — 이 기능만 특별히 더 정밀하게 만들 필요는 없다.
2. **요리 재료가 아닌 식품은 걸러낸다.** 완제품 간식·베이커리·음료처럼 "먹지만 조리에 안 쓰는" 품목은
   재료 목록에 넣지 않는다. 휴지·세제 같은 비식품과 같은 급으로 거른다.
3. **정규화·필터링은 프롬프트가 아니라 코드가 강제한다.** "프롬프트로 지시만 하고 안 지켜지면 조용히
   어긋난다"는 D-0r에서 이미 겪은 문제다. 다행히 새로 만들 필요가 없다 — `spec-recipe-match.md`가
   레시피 매칭을 위해 만드는 **재료 어휘 색인(정규화된 홈쿠킹 재료명 111,854종)**을 그대로 재사용하면
   된다. 추출된 이름을 이 어휘와 `find_owned()`로 대조해서, 어휘에 없으면 버리고(예: "마들렌" → 자동
   제외) 있으면 정규화된 이름으로 치환한다(예: "닭가슴살 볼" → "닭가슴살"). 새 분류기를 따로 만들지
   않는다.
   **단, 대조는 "어휘에 있나 없나"만으로 끝내지 않고 최소 등장 횟수를 함께 본다** — 234,538개
   레시피에서 사람들이 자유롭게 적은 원문이라 "도리토스"처럼 우연히 한 번 등장하는 비재료도 섞여
   있다(마트 영수증 실측 3차 참고). 등장 횟수가 문턱값(가칭 5회) 미만이면 어휘에 있어도 버린다.
4. **AI·코드 처리 결과는 반드시 사용자 확인을 거친다.** 지금까지 이 프로젝트가 AI 결과를 안전하게
   만든 방법은 "AI 결과를 사용자가 가진 것과 코드로 대조"하는 것이었는데, 이 기능은 추출 결과 자체가
   냉장고 목록이 되어 대조할 기준(정답)이 없다. 그래서 추출·필터링 결과를 바로 반영하지 않고, 사용자가
   보고 빼거나 고칠 수 있는 편집 가능한 목록으로 먼저 보여준 뒤 확정한다.
   **이건 선택 사항이 아니다.** 실측 중 "유부"로 잘못 추출된 항목이 실제론 어묵탕 재료였던 사례가
   나왔는데(§실측 결과, 마트 영수증), 이런 "재료는 맞는데 다른 재료로 오독"하는 오류는 핵심 원칙
   3(어휘 대조)으로도 못 걸러낸다 — 어휘 대조는 "재료냐 아니냐"만 판단하지 "정확히 뭔 재료냐"는
   검증하지 못하기 때문이다. 그러니 §4의 확인 화면은 생략 가능한 부가 UX가 아니라, 이 기능이
   정확하려면 반드시 있어야 하는 유일한 관문이다.
5. **날짜 정보가 있으면 신선도 태그에 활용한다.** 쿠팡 화면엔 주문일("2026. 8. 19 주문"), 영수증엔
   승인일자가 찍혀 있다. 지금은 "며칠 전에 넣음" 표시(`addedAt`)가 재료를 넣은 그날로만 자동 찍히고
   사용자가 직접 고칠 방법이 없는데(`js/shared.js`), 이 기능에서는 실제 구매일로 정확히 채울 수 있다 —
   단순 마찰 감소를 넘어서는 부가 가치다.

## 데이터 모델 — 기존 그대로 재사용

pantry 저장 형식은 이미 `{ name, amount, addedAt }` 세 칸이고, `addedAt`은 `YYYY-MM-DD` 문자열
또는 `null`을 허용한다(`js/shared.js`의 `toPantryItem`/`daysSince`). **이 기능은 새 스키마가
필요 없다** — 추출 결과를 이 형식에 맞게 만들어서 기존 `savePantry()`에 넣기만 하면 된다.

## 기능 설계

### 0. UI 배치

`pantry.html`은 지금 이 구조다.

```
h1 "내 냉장고"
section.pantry-page
  h2 "재료 넣기"
  p.pantry-hint
  div.pantry-input-row → input#pantry-input + button#pantry-add-btn("넣기")
  p#pantry-status
  div.pantry-list-head → h2 "지금 들어있는 재료" + button#pantry-amount-toggle
  div#pantry-chips
  div#pantry-empty (+ #pantry-examples)
```

**`.pantry-input-row` 바로 아래, `#pantry-status` 위**에 새 버튼을 하나 둔다. "재료 넣기" 섹션
자체가 입력 방법을 모아두는 자리이므로, 지금의 텍스트 입력과 같은 급의 대안으로 보이게 그 바로
아래 배치한다. 입력창 옆 한 줄에 아이콘 버튼으로 욱여넣지 않는다 — 지금 입력창 + "넣기" 버튼
한 줄이 이미 꽉 차 있어서 여기 더 넣으면 복잡해 보인다. 대신 라벨이 있는 별도 줄 버튼으로 둔다
(`.cta-button-secondary` 스타일 재사용 — `css/style.css:547`, `page-next` 섹션에서 이미 쓰는
클래스라 새 스타일을 안 만들어도 된다).

버튼 문구는 하드코딩하지 않고 `copy.js`에 새 키(예: `PANTRY.photoImportButton`)로 추가한다.
`pantry.html`은 전용 JS 파일이 따로 없고(`js/pantry.js` 없음) `#pantry-add-btn` 등 pantry 로직이
전부 `js/shared.js`에 있다(`body[data-page="pantry"]`로 분기) — 이 기능의 이벤트 처리도 새 파일을
만들지 않고 `js/shared.js`에 같이 넣는다.

빈 상태(`#pantry-empty`)에도 이 버튼이 계속 보이게 둔다 — 이 기능은 "처음 한 번" 쓰고 마는 게
아니라 장 볼 때마다 반복해서 쓰는 동작이라, 재료가 이미 들어있는 상태에서도 계속 눈에 띄어야 한다.

### 1. 입력 — 사진 업로드/촬영

`<input type="file" accept="image/*">`를 쓰되 **`capture` 속성은 넣지 않는다.** `capture="environment"`를
넣으면 모바일에서 카메라만 강제로 열려 갤러리에서 쿠팡 캡처 이미지를 고를 수 없게 된다. `capture`
없이 두면 모바일 OS가 "카메라로 촬영" / "갤러리에서 선택"을 함께 보여주는 기본 선택지를 띄운다 —
그러면 영수증 촬영이든 쿠팡 캡처 업로드든 **버튼 하나**로 다 처리되고, 두 채널용 버튼을 따로 만들
필요가 없다.

### 2. 추출 — 비전 API 호출 (1차 필터: 프롬프트)

새 서버리스 함수(예: `api/pantry_import.py`)가 이미지를 `gpt-4o-mini` 비전에 보내 상품명·구매일자
후보를 뽑는다. 지금 `_common.py`의 `call_openai()`는 텍스트 전용 메시지만 만들므로, 이미지 파트가
섞인 멀티모달 메시지를 만드는 부분은 새로 구현해야 한다.

프롬프트에는 "요리에 쓸 수 있는 식재료만 골라라, 완제품 간식·음료·비식품은 빼라"고 지시하되, 이건
느슨한 1차 필터일 뿐이다 — 실제 경계는 아래 3번이 코드로 긋는다.

### 3. 정규화 + 필터링 — 코드가 강제 (recipe-match 어휘 재사용) — 구현 완료 (2026-08-20)

```
추출된 이름들
  → 각각을 재료 어휘 색인(spec-recipe-match.md)과 find_owned()로 대조
  → 어휘에 없거나 최소 등장 횟수(가칭 5회) 미만이면 버림 (예: "마들렌", "도리토스" 1회)
  → 걸리면 어휘의 정규화된 이름으로 치환 (예: "닭가슴살 볼" → "닭가슴살")
```

`api/pantry_import.py`의 `normalize_and_filter()`가 이 그대로다. 어휘는 새로 만들지 않고
`recipe_match.vocab_with_min_occurrence(min_count)`로 recipe-match의 역색인을 그대로 불러
쓴다(`load_index()`가 이미 콜드 스타트에서 한 번만 읽어두는 것과 같은 캐시를 공유한다) —
**이 설계 때문에 이 기능은 recipe-match의 어휘 색인이 먼저 있어야 동작했는데**, 그 인덱스가
이미 배포 코드에 있어서 그대로 재사용했다.

비전 호출은 `api/_common.py`의 `call_openai()`에 `image_data_url` 인자를 추가하는 방식으로
얹었다 — 텍스트 전용으로 부르던 recommend.py·mealplan.py는 인자를 안 넘기므로 그대로 동작한다.
회귀 테스트는 `api/test_handlers.py`의 `test_pantry_import_*`·`test_call_openai_adds_image_part_when_given` 참고.

### 4. 확인 화면

새 페이지를 만들지 않고 `<dialog>` 요소로 띄운다. `mealplan.html`의 요일 상세(`#meal-dialog`,
`js/mealplan.js`)가 이미 같은 패턴이다 — 커스텀 오버레이 대신 네이티브 `<dialog>`의 `showModal()`을
쓰면 포커스 트랩·ESC 닫기·backdrop이 공짜로 딸려온다(`js/mealplan.js`의 주석 참고). 다만 CSS는
`.meal-dialog` 전용으로 스코프돼 있어(`css/style.css:1311`) 클래스를 그대로 공유하진 못한다 —
`.pantry-import-dialog` 같은 새 클래스를 만들되 `.meal-dialog`의 구조(backdrop, panel, head,
close 버튼)를 그대로 본떠서 톤을 맞춘다.

추출·필터링 결과를 바로 반영하지 않고, 체크박스로 편집 가능한 목록으로 보여준다.

```
[x] 닭가슴살        (2026-08-19 구매)
[x] 우유            (2026-08-19 구매)
[x] 계란            (2026-08-19 구매)
[ ] 마들렌          — 재료 사전에 없어 기본 체크 해제
```

사용자가 체크 해제·이름 수정 후 "냉장고에 담기"를 누르면 그제서야 각 항목을 `{ name, amount: "",
addedAt: 구매일 }` 형태로 만들어 `savePantry()`에 반영한다. 구매일 추출에 실패하면 오늘 날짜로
폴백한다. 수량(`amount`)은 이번 스펙 범위 밖이라 비워둔다.

## 엣지 케이스

- 흐리거나 잘려서 아무것도 못 읽은 사진 — 빈 결과 화면에도 브랜드 말투로 안내("사진이 흐릿해서
  재료를 못 읽었어요. 다시 찍어볼래요?" 류, `copy.js`에 새 키로 추가)
- 어휘에 하나도 안 걸려 추출 결과가 전부 걸러지는 경우(이번 빵집 영수증처럼) — "재료로 쓸 만한 게
  없어요"로 안내하고 수동 입력으로 유도
- 같은 영수증을 두 번 올려 중복 등록되는 경우 — 이번 스펙 범위 밖. 확인 화면에서 사용자가 걸러야
  한다(자동 중복 감지는 추후 논의)

## 범위 밖 (이번 스펙에 포함하지 않음)

- 수량(정확한 g·개수) 자동 인식 — 이름만 뽑는다
- 마트 체인별 축약 코드 사전 — gpt 비전의 일반 상식에 맡기고 별도 사전을 만들지 않는다
- 알레르기·비선호 재료 자동 제외 — 다른 스펙과 동일하게 범위 밖
- 쿠팡 외 다른 커머스(마켓컬리 등) 캡처 지원 — 쿠팡 하나로 먼저 검증하고 확장 여부는 나중에 판단

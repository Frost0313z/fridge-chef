# 스펙 — 실제 레시피 매칭 (KADX 데이터셋 기반, AI 생성은 폴백으로)

**상태**: 스펙 작성 (2026-08-17), 구현 전
**관련 논의**: 레시피 추천 신뢰도(재료 검증, `D-0r`) → 실제 레시피 코퍼스 필요성 → KADX 무료 레시피 데이터 확보 → 라이선스 검토

---

## 배경

레시피 추천(`api/recommend.py`)은 지금 100% AI가 그 자리에서 새로 만들어낸 결과다. 재료가
없는 걸 지어내는 문제는 `sanitize_recipes()`의 재료 검증(D-0r)으로 상당히 줄였지만, "이 요리가
정말 존재하고 맛있고 시간이 맞는가" 자체는 여전히 AI 생성물이라 근본적으로 검증할 수 없다.

이 문제를 풀려고 RAG(실제 레시피 코퍼스에서 후보를 찾고 AI는 그중에서 고르거나 다듬게 하는 방식)를
검토하다, KADX(농식품 빅데이터 거래소)에서 만개의레시피 원본 DB로 보이는 무료 데이터셋을
확보했다. 다만 라이선스가 **CC BY-NC-ND**(출처표시-비영리-변경금지)라, AI가 원문을 재구성해서
새 텍스트를 만들어내는 순간 ND(변경금지) 조항과 충돌한다. 그래서 "재료 매칭에는 이 데이터를
코드로만 쓰고, 조리 상세는 원문을 절대 재구성하지 않고 만개의레시피 링크로만 안내한다"는 설계로
정리했다 — 라이선스도 지키고, 오히려 AI 생성보다 신뢰도가 높은 결과(실제 존재하는 레시피)를
얻는다.

## 데이터 출처 및 라이선스

- **출처**: KADX 농식품 빅데이터 거래소, 상품명 "무료 레시피 데이터"
  (`https://kadx.co.kr/opmk/frn/pmumkproductDetail/PMU_6d212747-8bd4-42c2-bc55-60bc636d6121`)
- **원 테이블명**: `TB_RECIPE_SEARCH` — 컬럼명(`RCP_SNO`, `CKG_MTRL_CN` 등)이 코드성 약어인 것으로
  보아 웹 크롤링이 아니라 운영 DB를 직접 내보낸 덤프로 추정. `RCP_SNO`가 실제로
  `https://www.10000recipe.com/recipe/{RCP_SNO}`로 연결되는 것을 확인함(2026-08-17, 직접 fetch로 검증) — 만개의레시피 원본 데이터가 맞다.
- **라이선스**: CC BY(출처표시) - NC(비영리) - ND(변경금지)
  - **BY**: 링크 옆에 "레시피 출처: 만개의레시피(KADX 제공)" 표기로 충족
  - **NC**: 있는대로는 광고·결제가 없는 비영리 프로젝트라 지금은 문제 없음. **나중에 수익화하면 이
    데이터는 다시 쓸 수 없다** — 그 시점엔 별도 데이터로 교체해야 한다(서비스기획서 "향후 확장"에
    함께 적어둠)
  - **ND**: 원문(조리 소개글 `CKG_IPDC`, 조리 순서)을 AI에 넣거나 화면에 재구성해서 보여주지 않는다.
    **재료 목록(사실 데이터)으로 매칭 스코어만 계산하고, 상세 콘텐츠는 항상 원본 링크로 안내한다.**
    이 경계를 지키는 한 "2차적저작물을 만든다"고 보기 어렵다고 판단했으나, 법률 자문은 아니므로
    확신이 필요하면 KADX에 이 설계를 그대로 설명하고 확인받는 것을 권한다

## 핵심 원칙

1. **재료 매칭은 코드로, 상세 콘텐츠는 링크로.** 장보기 합산을 AI에서 코드로 옮긴 것과 같은 이유다
   — 겹치는 재료를 세는 건 애초에 AI가 할 일이 아니고, 이번엔 라이선스까지 그 방향을 요구한다.
2. **실제 매칭이 있으면 AI를 부르지 않는다.** `POST /api/shopping`이 이미 쓰는 패턴("재료를 아는
   메뉴는 AI에게 안 묻는다")과 같다. 비용·속도 둘 다 이득이다.
3. **AI 생성은 실제 매칭이 없을 때만 켜지는 폴백이다.** 지금의 `recommend.py` 로직은 사라지지
   않고, 순서만 뒤로 밀린다.
4. **원문 재구성 금지는 코드로 강제한다.** "프롬프트로 지시만 하고 안 지켜지면 조용히 어긋난다"는
   D-0r에서 이미 겪은 문제라, 애초에 `CKG_IPDC`·조리 순서 같은 원문 필드는 파이프라인에 들이지
   않는다 — 갖고 있지 않으면 실수로 새어 나갈 수도 없다.

|---|---|---|

| `CKG_IPDC` | 조리 소개글(창작적 서술) | ❌ 제외 — ND 위험이 가장 큰 필드. 파이프라인 첫 단계에서 버린다 |
| `RGTR_ID` / `RGTR_NM` | 등록자 ID/닉네임 | ❌ 제외 — 매칭에 불필요하고 개인 식별 정보라 굳이 들고 있을 이유가 없다 |
| `INQ_CNT` | 조회수 | ❌ 제외 — 추천수·스크랩수로 충분, 굳이 세 지표를 다 안 들고 감 |
| `FIRST_REG_DT` | 최초 등록일 | ❌ 제외 — 두 스냅샷 파일 중 하나(`241226`)에서 `2.02401E+13`처럼 지수표기로 깨져 있음(엑셀에서 열었다 저장하며 손상된 것으로 보임). 이번 기능엔 필요도 없어서 그냥 버린다 |

## 기능 설계

### 1. 데이터 파이프라인 (배포 전 1회 처리, 요청마다 하지 않음)

```
CSV 2개(23,192건 + 26,093건, RCP_SNO 기준 중복 제거, 최신 파일 우선)
  → 위 표의 "제외" 필드 제거
  → CKG_MTRL_CN 파싱: "[재료] " 접두사 제거 → "|"로 분리 → 각 조각을 이름+수량+단위로
     (shopping.py의 parse_line()과 최대한 같은 규칙을 쓴다 — 표기가 갈리면 매칭이 안 맞는다)
  → 재료명 배열이 비었거나(파싱 실패) CKG_NM이 빈 레시피는 버림
  → 경량 포맷(JSON)으로 저장, api/ 옆 정적 데이터로 배포에 포함
```

### 2. 매칭 로직 (`api/recommend.py`가 AI를 부르기 전에 먼저 시도)

1. 사용자 입력 재료를 정규화(`shopping.normalize_name`)
2. 각 후보 레시피의 재료 배열과 `shopping.find_owned()`로 겹침 판정(D-0r에서 레시피 검증에
   재사용한 것과 같은 함수 — 규칙을 세 번째 갈라 쓰지 않는다)
3. **커버율 = 사용자가 가진 재료로 충족되는 레시피 재료 수 / 레시피 전체 재료 수**
4. 커버율이 기준(예: 70% 이상, 정확한 값은 실측 후 조정) 이상인 후보만 남기고, 여러 개면
   `RCMM_CNT + SRAP_CNT`로 정렬해 상위 몇 개만 사용
5. 후보가 하나 이상이면 **AI를 호출하지 않고** 그 결과를 반환. 후보가 없으면 지금과 동일하게
   `call_openai()`로 폴백

### 3. 응답 스키마에 `source` 추가

```json
{
  "recipes": [
    {
      "name": "소고기떡국",
      "source": "matched",
      "recipeUrl": "https://www.10000recipe.com/recipe/7016813",
      "time": "30분이내", "portion": "2인분", "ingredients": ["떡국떡", "다진소고기", "..."],
      "steps": []
    },
    {
      "name": "AI가 새로 만든 요리",
      "source": "generated",
      "searchKeyword": "...", "time": "15분", "ingredients": ["..."], "steps": ["...", "..."]
    }
  ]
}
```

`source: "matched"`인 항목은 `steps`를 비워두고(원문을 재구성하지 않으므로), 프론트는 조리
순서 대신 "만개의레시피에서 자세히 보기 →"를 **주 CTA**로 보여준다. 링크 옆엔 BY 조건에 따라
출처를 표기한다("레시피 출처: 만개의레시피"). 이 문구도 프로젝트 규칙대로 `js/copy.js`에
새 키로 추가해야 한다(하드코딩 금지).

### 4. AI 프롬프트 — 폴백 역할을 명시하는 문단 추가

매칭 로직이 붙으면 `recommend.py`의 `call_openai()` 호출부는 **매칭이 실패했을 때만** 실행된다
(구조상 항상 그렇게 되므로, 런타임에 "이번이 폴백인지" 따로 분기할 필요는 없다 — 함수 자체가
폴백 경로가 된다). 그래서 `SYSTEM_PROMPT`에 그 전제를 알려주는 문단을 하나 더해 AI가 여전히
사용자 재료와 동떨어진 창작으로 흐르지 않고, 있는 재료를 최대한 살리는 쪽을 우선하게 한다.
새로 추가되는 문단만 `+`로 표시했고, 나머지는 지금 `api/recommend.py`의 `SYSTEM_PROMPT`와 동일하다.

```python
SYSTEM_PROMPT = """당신은 냉장고에 있는 재료로 만들 수 있는 한식/양식/중식 요리를 추천하는 요리 도우미입니다.
사용자가 알려준 재료를 최대한 활용하는 요리 1~3개를 추천하세요.
소금, 후추, 식용유, 물처럼 대부분의 가정에 있는 기본 조미료는 목록에 없어도 사용할 수 있다고 가정합니다.
사용자가 알려주지 않은 값비싸거나 특수한 재료를 임의로 추가하지 마세요.

+당신은 실제로 존재하는 레시피 중에 이 재료 조합과 충분히 겹치는 것이 없어서 대신 호출됐습니다.
+그러니 완전히 새로운 요리를 창작하기보다, 사용자가 가진 재료를 최대한 그대로 살리는 조합을
+우선하세요. 특이하거나 낯선 조합보다, 평범해도 실제로 이 재료들로 바로 만들 수 있는 요리가
+더 낫습니다.

사용자는 혼자 사는 자취생입니다. 이건 선택 사항이 아니라 항상 참인 전제입니다.
설거지가 적고 조리 과정이 간단한 요리를 우선하고, 특수한 조리도구가 필요한 요리는 피하세요.

재료 옆에 "(13일 전에 넣음)"처럼 냉장고에 들어온 지 오래됐다는 표시가 붙어 있을 수 있습니다.
그 재료는 곧 상해서 버리게 될 가능성이 높으니, 그것을 쓰는 요리를 반드시 먼저 추천하세요.
표시가 없는 재료는 최근에 넣은 것이라 급하지 않습니다. 재료를 버리지 않게 하는 것이
이 서비스의 목적이므로, 맛보다 이 순서를 우선합니다.

searchKeyword는 레시피 사이트에서 검색할 때 쓰는 값입니다. 수식어를 빼고 널리 쓰이는 짧은 요리 이름만
적으세요 (예: name이 "냉장고털이 두부 계란 덮밥"이면 searchKeyword는 "두부덮밥"). 검색어가 길면
엉뚱한 결과가 나오므로 되도록 두 단어를 넘기지 마세요.

반드시 아래 JSON 형식으로만 응답하세요. 다른 설명 문장을 추가하지 마세요.
{
  "recipes": [
    {
      "name": "요리 이름",
      "searchKeyword": "검색용 짧은 요리 이름",
      "time": "예상 조리 시간 (예: 15분)",
      "ingredients": ["재료1", "재료2"],
      "steps": ["조리 순서 1", "조리 순서 2"]
    }
  ]
}"""
```

새 문단을 "임의로 추가하지 마세요" 바로 다음, "혼자 사는 자취생" 문단 앞에 둔 이유는 재료 관련
지시들(뭘 쓰고 뭘 안 써야 하는지)을 한데 모아두기 위해서다 — 상황 설명(자취생·설거지)과 섞으면
읽는 순서상 재료 규칙이 흩어져 보인다. `source: "generated"`로 나가는 응답은 지금과 형식이
같으므로 `sanitize_recipes()`나 프론트 렌더링 쪽은 손댈 필요가 없다 — 프롬프트 문단만 늘어난다.

## 구현 전 확인 사항 — 원래 질문 (답은 다음 절에)

1. **Vercel 서버리스 함수 번들 크기.** 원본 CSV가 합쳐서 25MB대다. 전처리로 줄이더라도 정적
   데이터 파일이 함수 배포 크기 제한에 걸리는지, 걸린다면 얼마나 더 줄여야 하는지(불필요 필드
   제거만으로 충분한지, gzip으로 충분한지) 실측이 필요하다.
2. **`CKG_MTRL_CN` 파싱이 `shopping.py`의 `parse_line()`과 얼마나 호환되는지.** 표본 100건
   정도를 실제로 파싱해서, 이 데이터셋 특유의 단위 표기(예: 이 데이터가 `1큰술`을 `1T`로 줄여
   쓰는 경우가 샘플에서 보였다 — `_UNITS` 목록에 없는 표기)가 있는지 확인하고 필요하면
   `_UNIT_ALIASES`에 추가해야 한다.
3. **두 스냅샷(`241226`, `251231`) 병합 시 실제 중복률.** `RCP_SNO` 기준으로 얼마나 겹치는지,
   최신 파일에서 값이 달라진 레코드가 있는지 확인 후 병합 규칙을 확정한다.
4. **커버율 임계치(70% 가정)가 적절한지.** 너무 높으면 매칭이 거의 안 걸려 AI 폴백만 계속 돌고,
   너무 낮으면 "재료 절반도 없는데 매칭됐다"고 사용자가 느낄 수 있다. 실제 데이터로 몇 차례
   조정이 필요하다.

## 구현 전 확인 사항 — 실측 완료 (2026-08-17)

원래 적어둔 1~3번을 실제 데이터로 재봤다. **네 가지가 스펙과 달랐다.**

### ⓐ 데이터가 생각보다 훨씬 많다 — 49,285건이 아니라 233,283건

`data/kadx-recipes/`의 두 파일 말고 **저장소 루트에 CSV 두 개가 더 있었다**(합쳐서 156MB).

| 파일 | 크기 | 레시피 수 |
|---|---|---|
| `TB_RECIPE_SEARCH-220701.csv` | 52.8MB | 128,400 |
| `TB_RECIPE_SEARCH-231130.csv` | 77.8MB | 184,991 |
| `TB_RECIPE_SEARCH_241226.csv` | 11.1MB | 23,192 |
| `TB_RECIPE_SEARCH_251231.csv` | 13.4MB | 26,093 |

**네 스냅샷은 서로 겹치지 않는다.** `RCP_SNO` 기준으로 합치면 **234,538건**이고,
`251231`은 `231130`과 **한 건도 겹치지 않는다**(26,093건 전부 새것). 부분집합이 아니라
기간별 증분 스냅샷이다. 따라서 "최신 파일 우선으로 중복 제거"라는 규칙은 맞지만,
**두 개만 쓰면 코퍼스의 79%를 버리게 된다.** 네 개를 다 병합한다.

### ⓑ `CKG_MTRL_CN`은 이미 파싱돼 있다 — `parse_line`으로 다시 자르면 안 된다

스펙은 `"[재료] 계란2개| 대파..."`처럼 이름과 수량이 붙어 있다고 봤지만, 실제 값에는
**``(BEL)이 구분자로 들어 있다.**

```
실제:  [재료] 소고기100g| 불린미역50g| 참기름조금
보이는 것:  [재료] 소고기100g| 불린미역50g| 참기름조금      ← 터미널이 BEL을 안 보여줄 뿐
```

즉 원본이 **이름 · 수량 · 단위를 이미 나눠놨다.** 이걸 모르고 `parse_line()`에 넣으면
이름이 `'소고기 g'`로 나온다 — 매칭이 통째로 어긋난다.

**하위 그룹 머리말도 있다.** `[재료]` 접두사 하나만 있는 게 아니라 `[비빔밥 고추장양념]`,
`[생굴 세척]`처럼 중간에도 들어간다(표본의 **44.2%**). `\[[^\]]*\]`를 전부 구분자로 바꿔야 한다.

**확정한 파싱 규칙** — ``로 자르고, 그러고도 이름에 수량이 붙어 있는 경우가 있어
(`"양파 1/2개"`) 이름 쪽만 한 번 더 `parse_line()`에 통과시킨다. 둘을 합쳤을 때:

| | 서로 다른 재료명 |
|---|---|
| `parse_line`만 (스펙 원안) | 283,609종 — 이름에 ``·단위가 섞여 사실상 못 씀 |
| `` 분리 + `parse_line` 정리 | **118,862종**, 상위 12종이 `양파·소금·설탕·다진마늘·참기름·물·대파·후추·간장·계란·당근·청양고추` |

재료를 하나도 못 뽑는 레시피는 **0.48%**뿐이라 그냥 버리면 된다.

`1T`/`1t` 문제는 실재한다(단위가 `_UNIT_ALIASES`에 없어 이름에 남는다). 다만 매칭은
**이름만** 쓰므로 수량 단위는 급하지 않다 — 나중에 수량까지 쓸 때 정리한다.

### ⓒ 번들 크기 — 통과

233,283건을 `{id, name, ing[], time, inbun, pop}`만 남겨 직렬화한 결과:

| | 크기 |
|---|---|
| JSON | 48.5MB |
| JSON + gzip(9) | **9.4MB** |

Vercel 서버리스 함수 상한(압축 250MB)에 여유 있게 들어간다. **다만 콜드 스타트마다 48MB를
읽어 파싱하는 비용은 따로 재봐야 한다** — 이번 실측 범위 밖이고, 필요하면 재료명 역색인만
올리는 쪽으로 줄인다.

### ⓓ 커버율 임계치는 아직 미확정

파이프라인을 붙인 뒤 실제 냉장고 조합으로 재야 한다. 원래 적어둔 대로 실측 후 조정한다.

## 실측 2차 — 프리뷰 배포에서 잰 것 (2026-08-19, A안 그대로)

233,283건 · 48.5MB JSON을 그대로 올려 프리뷰 배포(`vercel`, `--prod` 없이)에서 쟀다.

### 결론: 콜드 스타트는 문제가 아니었다. 요청당 스캔이 문제다.

| 구간 | 시간 |
|---|---|
| 인덱스 로드 (`json.load` 48.5MB, 콜드 1회) | **686 ms** |
| 요청당 매칭 — 재료 3개 | 787 ms |
| 요청당 매칭 — 재료 5개 | 1,481 ms |
| 요청당 매칭 — 재료 7개 | **2,233 ms** |

프리뷰 배포 실측(왕복):

| | 왕복 | 함수 실행(로그) |
|---|---|---|
| 콜드 (첫 요청) | 5.1 s | ~4.3 s |
| 웜 (연속 3회) | 3.34 / 3.23 / 3.30 s | ~2.5–2.8 s |

**콜드와 웜의 차이가 0.7초뿐이다.** 로드 비용은 예상대로 작았고(686ms), 남는 2.5초는
컨테이너가 더워져도 사라지지 않는 **매 요청 비용**이다. 원인은 23만 건 × 재료 수만큼
`find_owned()`를 도는 완전 스캔이고, 재료가 늘수록 선형으로 늘어난다(3개 787ms → 7개 2,233ms).

**이건 이 기능의 목적을 깎아먹는다.** 매칭을 넣은 이유 중 하나가 "AI를 안 부르니 빠르다"였는데,
같은 조건에서 실제 AI 호출이 4.4초였다. 2.5초는 이득이 거의 없다.

→ **B안(색인)으로 간다. 손으로 역색인을 짜기 전에 SQLite를 먼저 검토한다** — 표준 라이브러리라
새 의존성이 없고, 파일 하나로 랜덤 액세스가 되며, `json.load` 686ms 자체가 사라진다.

### 함께 드러난 것

- **`.vercelignore`가 필요했다.** Vercel CLI는 `.gitignore`를 보지 않고 로컬 폴더를 통째로
  올린다. 원본 CSV 181MB가 같이 올라가 **번들 288MB로 상한(225MB)을 넘겨 배포가 실패**했다.
  `.vercelignore`에 `data/`·`TB_RECIPE_SEARCH*.csv`·`docs/`·`scripts/`를 넣어 해결.
- **`includeFiles` 설정이 필요했다.** `@vercel/python`이 엔트리포인트 옆 파일을 자동으로
  다 넣어주지 않아 `vercel.json`의 build config에 `"includeFiles": "api/**"`를 넣었다.
- **결과 품질에 문제가 있다** — 아래 세 가지는 색인 작업과 별개로 고쳐야 한다.

| 증상 | 예 | 원인 |
|---|---|---|
| 같은 이름이 여러 번 | `김치밥` 2건, `만능간장` 3건 | 서로 다른 `RCP_SNO`라 중복 제거에 안 걸린다. 이름 기준 dedupe가 필요 |
| 재료 적은 레시피가 독식 | `김치밥(밥·신김치·참기름)` 100% | 커버율은 분모가 작을수록 유리하다. `MIN_INGREDIENTS = 3`으론 부족 |
| 단위가 이름에 남음 | `참기름T` | `T`/`t`(큰술/작은술)가 `_UNIT_ALIASES`에 없다 |

## 품질 3건 정리 (2026-08-19) — SQLite 이전에 먼저 한 것

저장소 종류와 무관한 문제들이라 JSON 선형 스캔 상태에서 먼저 고쳤다. 특히 파싱 버그는
코퍼스 자체에 박히는 문제라, SQLite로 옮긴 뒤에 고치면 인덱스를 다시 만들어야 한다.

### bug 3 — 단위가 이름에 눌러앉던 문제 (`참기름T`)

레시피 데이터가 큰술/작은술을 `T`/`t`로 줄여 쓰는데 `_UNITS`에 없어서 단위로 못 읽고
이름에 남았다. `T`·`t`·`L`을 목록과 별칭에 넣었다.

**대소문자를 구분해서 받는다** — `T`(큰술)와 `t`(작은술)는 양이 세 배 차이라 하나로 묶으면
수량이 틀어진다. `L`은 기존 `l → ml` 배율로 흘려보낸다.

`js/shared.js`의 `AMOUNT_UNITS`·`UNIT_ALIASES`에도 같이 넣었다 — 한쪽만 알아보면 같은 재료를
서로 다르게 읽는다. 두 파서가 같은 답을 내는 것을 실측으로 확인했다(`참기름1T` → 1큰술,
`물1.5L` → 1500ml 양쪽 동일).

재빌드 후 `참기름T`는 0회, `참기름`은 54,088회가 됐다.

> [!NOTE]
> 이 버그의 실제 피해는 **매칭이 아니라 화면 표시**였다. `find_owned`의 포함 비교가
> `"참기름" in "참기름T"`로 이미 건져내고 있었기 때문이다. 그래도 사용자에게 보이는
> 재료 이름이라 고치는 게 맞다.

### bug 1 — 같은 이름이 여러 장 (`김치밥` 2건, `만능간장` 3건)

**인덱스에서 합치지 않는다.** `RCP_SNO`가 다르면 실제로 다른 레시피이고("만능간장"이라는
이름의 서로 다른 레시피가 진짜로 여럿 있다), 합치면 데이터를 잃는다.
**화면에 같은 이름 카드가 여러 장 뜨는 것만** `match()`에서 막는다.

판정은 추천 이력·즐겨찾기가 쓰는 `dedupe_key`를 그대로 쓴다 — "김치볶음밥"과 "김치 볶음밥"은
같은 요리다. 규칙을 네 번째로 갈라 쓰지 않는다.

> **SQLite 스키마에 주는 답**: 고유 제약(UNIQUE)은 **`RCP_SNO` 하나**다. 이름은 유니크가
> 아니고, 이름 중복 제거는 **조회 시점**의 관심사다. 인덱스는 전부 들고 있고 질의가 골라낸다.

### bug 2 — 재료 적은 레시피 독식

커버율(%)만으로 줄을 세우면 분모가 작을수록 유리해서 `김치밥(밥·신김치·참기름)` 같은 3개짜리가
늘 100%로 이겼다. 제안대로 **매칭된 절대 개수를 함께 본다.**

```
점수 = (hit / total) × hit
```

재료 3개를 다 맞추면 `(3/3)×3 = 3`점, 8개 중 7개를 맞추면 `(7/8)×7 = 6.1`점이다.
커버율은 후자가 낮지만 냉장고를 더 많이 쓴다 — **"있는 재료를 최대한 활용한다"** 는
서비스 목적과 같은 방향이다. `MIN_COVERAGE = 0.7`·`MIN_INGREDIENTS = 3`은 그대로 뒀다.

**전후 비교** (냉장고: 두부·김치·대파·계란·밥·참기름·양파)

| 이전 | 이후 |
|---|---|
| 김치밥 (재료 3개) | **순두부찌개** (재료 8개, 88%) |
| 김치밥 (재료 3개, 이름 중복) | **참치김치볶음밥** (재료 7개, 86%) |
| 파김치찌개 (재료 5개) | **두부계란밥** (재료 7개, 86%) |

### 남은 파싱 잡음 — 이번엔 손대지 않음

같은 부류가 더 있지만 심각도가 다르다. 전체 재료 조각 2,167,755개 기준:

| 잡음 | 고유 이름 | 등장 | 예 |
|---|---|---|---|
| `적당량`류 | 5,933종 | 32,221회 | `식용유적당량` |
| `~` | 5,129종 | 22,514회 | `청양고추~`, `물~` |
| `또는`/`or` 결합 | 6,961종 | 11,224회 | `원당또는설탕` |
| `cup`/`oz` 등 | 356종 | 827회 | `물cup` |

합쳐도 약 3%이고, **대부분 `find_owned`의 포함 비교가 이미 건져낸다**
(`"식용유" in "식용유적당량"`). 다만 한 글자 재료는 방어 규칙에 걸려 못 건진다(`물~` ↔ `물`).
급하지 않다고 보고 남겨둔다.

## 엣지 케이스

- **매칭된 레시피의 링크가 죽어 있음** (스냅샷 이후 원본이 삭제/비공개 전환됨) — `recipeUrl`
  접속 실패를 프론트에서 감지할 방법은 마땅치 않으므로, 지금의 AI 생성 레시피가 쓰는 검색 링크
  패턴(`CKG_NM`으로 검색 URL 구성)을 폴백으로 함께 내려보내는 것을 고려한다.
- **매칭 결과와 AI 생성 결과가 한 응답에 섞이는 경우** — 후보가 부족해서(예: 2개만 매칭) AI로
  나머지를 채우는 상황. `MAX_RECIPES = 3`을 유지하되 `source`를 섞어서 보내는 걸 허용할지,
  아니면 "매칭 있으면 매칭만, 없으면 생성만"으로 딱 자를지는 구현 시 결정한다 — 후자가 더 단순하다.
- **사용자가 알레르기·비선호로 특정 재료를 뺀 경우** (`healthy` 옵션처럼) — 매칭 로직은 지금
  "가진 재료로 커버되는가"만 보므로, 안 좋아하는데 우연히 다 가진 재료 조합의 레시피가 매칭될
  수 있다. 이번 스펙 범위에서는 다루지 않는다(아래 "범위 밖" 참고).

## 범위 밖 (이번 스펙에 포함하지 않음)

- 벡터 임베딩 기반 의미 검색 — 재료 겹침 스코어링(코드)만으로 이번 목적엔 충분하다고 판단
- 만개의레시피 실시간 연동(공식 API 없음, 이미 확인됨) — 이번 스펙은 스냅샷 데이터만 쓴다
- 데이터셋 정기 갱신 자동화 — 수동으로 새 스냅샷을 받아 파이프라인을 다시 돌리는 것으로 충분
- 선호/비선호 재료 반영, 알레르기 필터 — 별도 논의 대상
- 수익화 시나리오 — NC 조건 때문에 그 시점엔 이 데이터셋 자체를 못 쓴다. 별도 데이터 소싱이
  필요하고, 이건 서비스기획서 "향후 확장"에서 다룬다

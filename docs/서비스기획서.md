# 서비스 기획서 — 냉털 셰프 (fridge-chef)

## 1. 서비스 개요

### 문제 정의

자취생에게는 "식비를 아끼고 싶다"는 근본적인 욕망이 있습니다. 매 끼니 배달을 시키면 돈이 계속
나가기 때문에, 가능하면 직접 해먹어서 지출을 줄이고 싶어 합니다. 하지만 이 욕망은 세 개의 장벽
앞에서 막힙니다.

```
"식비를 아끼고 싶다" (자취생의 진짜 욕망)
        │
        ▼
직접 해먹으려고 시도
        │
        ├──▶ 장벽 1: 냉장고에 뭐가 있는지 파악이 안 됨
        │              (뭘로 뭘 만들 수 있는지 모름)
        │
        ├──▶ 장벽 2: 뭘 사야 할지 몰라서 장보기 계획을 못 세움
        │              (마트든 쿠팡이든 "필요한 것만" 사는 게 아니라
        │               감으로 사서 겹치거나 빠뜨림)
        │
        └──▶ 장벽 3: 쿠팡 등 온라인 주문은 당일이 아니라 다음날 도착
                       → 오늘 먹을 끼니는 결국 해결이 안 됨
                       │
                       ▼
              "일단 오늘은 시켜먹자" → 배달 주문
                       │
                       ▼
        식비는 오히려 더 나가고, 이미 쟁여둔 재료는 계속 방치
                       │
                       └──────────▶ (다음 끼니, 다시 반복)
```

이 서비스는 세 장벽을 모두 다룹니다. **장벽 1**(냉장고 파악 안 됨)은 재료 입력 → AI 추천(레시피
추천 페이지)으로, **장벽 2·3**(장보기 계획 부재, 쿠팡 다음날 배송)은 재료함을 반영해 며칠치
식단을 미리 짜고 부족한 재료만 뽑아주는 주간 식단 계획 페이지로 해소합니다.

이 서비스의 진짜 가치는 "AI가 레시피를 추천해준다"는 기능 자체가 아니라, **자취생이 원래 갖고
있던 "식비 절약" 욕망을 실제로 실현 가능하게 만들어주는 것**입니다. 장벽을 없애줌으로써 배달
대신 직접 요리를 선택하게 하고, 결과적으로 돈을 아끼게 돕습니다.

| 항목 | 내용 |
|---|---|
| 서비스명 | 냉털 셰프 (냉장고 털기 + 셰프) |
| 한 줄 정의 | 냉장고에 있는 재료만 입력하면 AI가 지금 만들 수 있는 요리를 추천해주는 웹 서비스 |
| 목적 | 식비를 아끼고 싶지만 "냉장고 파악 안 됨 + 장보기 귀찮음" 때문에 결국 배달에 의존하게 되는 악순환을, 재료 파악의 장벽을 없애서 끊는다 |
| 타겟 사용자 | 식비를 아끼고 싶어서 직접 해먹으려 하지만, 냉장고 재고 파악과 장보기의 번거로움 때문에 자주 배달로 타협하게 되는 20대 1인 가구 자취생 (기획자 본인이 실제 타겟이자 첫 사용자) |
| 진짜 경쟁 상대 | 다른 레시피 검색 서비스가 아니라 **배달 앱**이다. 레시피 사이트는 "요리 이름"으로 검색하는 구조라 "가진 재료로 뭘 만들 수 있나"라는 역방향 질문에 약하고, 배달 앱은 그 고민 자체를 없애주지만 돈이 들고 재료는 계속 방치된다. 이 서비스는 "가진 재료 → 즉시 요리 결정"을 배달만큼 빠르게 제공해서, 배달 대신 요리를 선택하게 만드는 것이 차별점이다 |
| 핵심 가치 | "AI 추천"이 아니라 "식비 절약 욕망의 실현" — 재료 파악 장벽만 없애주면 나머지(장보기 회피, 배달 의존)는 자연히 줄어든다는 가설 |
| 재방문 동기 | 하루 최소 1~2끼(점심/저녁)마다 반복되는 수요이므로, 한 번 습관이 되면 매일 쓸 이유가 생긴다. "내 재료함"·"최근 추천 이력"은 이 반복 사용을 전제로 매번 재입력하는 마찰을 없애기 위해 추가한 기능이다 |

## 2. 페이지 구성 및 메뉴 이동

5개 페이지, 상단 네비게이션(데스크톱은 가로 메뉴, 640px 이하 모바일은 햄버거 토글 메뉴)으로 이동한다.
**각 화면은 하나의 책임만 진다.** 네비 순서는 실제 사용 순서와 같다.

| 페이지 | 경로 | 단일 책임 |
|---|---|---|
| 홈 | `index.html` | 서비스 첫인상, 이용 방법 3단계, FAQ, 각 기능 진입점 |
| 냉장고 | `pantry.html` | 재료를 넣고 빼고 한눈에 보기 — **재료를 편집할 수 있는 유일한 화면** |
| 레시피 추천 | `recipe.html` | 오늘 뭐 해먹을지 정하기 (장벽 1 해소) |
| 식단 계획 | `mealplan.html` | 며칠치 아침·점심·저녁 정하기, 짠 뒤 직접 고치기 (장벽 2 해소) |
| 장보기 | `shopping.html` | 살 것 확인하고 사러 가기 (장벽 2·3 해소) |

### 데이터 흐름 — 냉장고가 단일 출처

```
                    ┌─────────┐
                    │   홈    │   진입점 전용 · 저장하는 데이터 없음
                    └────┬────┘
                         │ 안내만 한다
          ┌──────────────┴──────────────┐
          ▼                             ▼
    ┌──────────┐                  ┌──────────┐
    │  냉장고  │◀──── "샀어요" ───│  장보기  │
    │  (편집)  │                  │ (표시만) │
    └────┬─────┘                  └────▲─────┘
         │ 읽기 전용                    │ 읽기
    ┌────┴──────┐                       │
    ▼           ▼                       │
┌────────┐ ┌─────────┐                  │
│ 레시피 │ │  식단   │── 계획+장보기 ───┘
│  추천  │ │  계획   │    목록을 저장
└────────┘ └─────────┘
   (잎)      (중계자)
```

화면마다 관계 안에서의 성격이 다르다.

| 화면 | 성격 | 관계 |
|---|---|---|
| 홈 | 진입점 | 어느 데이터도 만들지 않는다. 두 갈래(냉장고 채우기 / 바로 추천받기)로 보낼 뿐 |
| 냉장고 | **단일 출처** | 재료를 편집하는 유일한 곳. 나머지 네 화면은 읽기만 한다 |
| 레시피 추천 | 소비자(잎) | 냉장고를 읽지만 아무것도 돌려주지 않는다. 결과는 자기 이력에만 남는다 |
| 식단 계획 | **중계자** | 냉장고를 읽어 결과를 저장하고, 그 저장분이 장보기의 입력이 된다 |
| 장보기 | 표시자 | 스스로 계산하지 않는다. 식단이 저장해 둔 목록을 그리고, "샀어요"로 냉장고에 되돌린다 |

**저장소 소유권** — 누가 쓰고 누가 읽는지를 고정한다. 쓰는 곳이 여럿이면 어느 값이 진짜인지 알 수 없어진다.

| 키 | 쓰는 곳 | 읽는 곳 |
|---|---|---|
| `pantry` | 냉장고, 장보기("샀어요") | 전 화면 조회 바, 레시피 추천, 식단 계획 |
| `mealplan` | 식단 계획 | 장보기 |
| `history` | 레시피 추천 | 레시피 추천 (자기만) |
| `prefs` | 레시피 추천 · 식단 계획 | 레시피 추천 · 식단 계획 (**공유**) |

`prefs`를 공유하므로 **분량**과 **건강 관리 중** 체크는 한쪽에서 바꾸면 다른 쪽에도 반영된다.
같은 질문을 두 번 하지 않기 위해서다. 반면 **조리 시간**은 레시피 추천에만, **일수**는 식단 계획에만 있다.

**서버 호출** — AI를 부르는 화면은 둘뿐이다.

| 화면 | API |
|---|---|
| 레시피 추천 | `POST /api/recommend` |
| 식단 계획 | `POST /api/mealplan` — 식단과 장보기 목록을 **한 번에** 받는다 |
| 장보기 | `POST /api/shopping` — 사용자가 식단을 고친 뒤 **목록만** 다시 받는다 (버튼을 눌렀을 때만) |
| 홈 · 냉장고 | 호출 없음 |

무엇을 살지는 **수량 판단**이 필요하다(냉장고에 "계란 2개"가 있어도 5일치에 8개가 필요하면 사야 한다).
프론트의 이름 대조로는 이 구분이 안 되므로 판단은 언제나 서버가 한다. 그래서 장보기 화면은 평소에
계산하지 않고 받아둔 목록을 그리기만 하다가, **사용자가 식단을 고쳤을 때만** 다시 뽑는다.
편집할 때마다 자동으로 부르지 않는 이유는 느려지고 비용이 계속 나가기 때문이다 — 부를 시점은 사용자가 정한다.

**두 AI 기능은 시간 축이 다르다.**

|  | 레시피 추천 | 식단 계획 |
|---|---|---|
| 범위 | 오늘 지금 한 끼 | 며칠치 세 끼 (3·5·7일 x 아침·점심·저녁) |
| 재료 출처 | 냉장고 **+ 오늘만 있는 재료**(직접 입력) | 냉장고 **만** |
| 결과의 수명 | 이력 5개 | 저장되어 장보기로 이어진다 |

**의도한 비대칭 세 가지** — 알고 둔 차이이므로 기록해 둔다.

1. **오늘만 있는 재료는 식단에 들어가지 않는다.** 추천 화면의 직접 입력은 그 요청 한 번만 쓰이고
   저장되지 않는다. 계속 쓰려면 냉장고에 넣어야 한다.
2. **재료 상한이 다르다.** 추천은 상한이 없고, 식단은 앞의 30개만 쓴다(프롬프트가 날짜 수만큼
   길어지기 때문). 이 차이를 사용자에게 알리지 않는 것은 남은 과제다 — UI/UX 원칙 체크리스트 17번.
3. **보유 판정 주체가 다르다.** 추천 카드의 "사야 해요" 표시는 프론트가 **이름으로** 판단하고,
   장보기 목록은 서버가 **수량까지** 따진다. 그래서 추천에서는 "있음"인데 장보기에 뜰 수 있다 —
   양이 모자란 경우다.

레시피 추천·식단 계획·장보기 세 화면은 모두 "지금 냉장고에 뭐가 있는지"를 알아야 판단이 되므로,
헤더 아래에 **접이식 조회 바**를 상시 배치한다. 접힌 상태에서도 요약(`계란, 대파 외 3개`)이 보이고
펼치면 전체 목록이 나오지만 **편집은 불가능하다** — 추가·삭제는 냉장고에서만 한다.

**빈 상태의 유도 동선도 이 고리를 따른다.** 막다른 길을 만들지 않기 위해, 각 화면이 비었을 때
다음 한 걸음을 가리킨다: 장보기가 비면 → "식단 계획하러 가기", 냉장고가 비면 → "냉장고를 먼저
채워보세요", 냉장고를 채우고 나면 → "이 재료로 추천받기 / 이번 주 식단 짜기".

> 초기에는 "소개"(`about.html`)가 별도 페이지였습니다. 이용 방법 3단계·기술 스택·FAQ를 담았는데,
> **홈의 기능 카드 3개와 소개의 이용 방법 3단계가 사실상 같은 내용을 두 번 말하고** 있었습니다.
> 카테고리를 줄여 인지 부하를 낮추기 위해 홈으로 통합하면서 두 블록을 하나로 합쳤고,
> 기술 스택은 사용자에게 필요한 정보가 아니므로 FAQ 항목으로 접어 넣었습니다.
> 상세는 아래 "페이지 통합"·"책임 단위 재편" 참고.

## 3. AI 기능 설계

**기능명**: 재료 기반 요리 추천

- **입력**
  - 보유 재료 (필수, 자유 텍스트, 쉼표로 구분 — 예: "계란 2개, 대파 조금, 두부 반모")
  - 만들 분량 (선택, 기본값 한 끼 — 혼자 먹는 전제이므로 "인원수"가 아니라 "몇 끼 분량"으로 묻는다)
  - 건강 관리 여부 (선택, 체크박스)
  - 희망 조리 시간 (선택, 기본값 상관없음)
- **처리**
  - 서버(`api/recommend.py`)가 입력을 받아 OpenAI Chat Completions API에 "이 재료로 만들 수 있는 요리 1~3개를 JSON으로만 응답하라"는 프롬프트를 전달한다.
  - 소금·후추·식용유·물 같은 기본 조미료는 없어도 있다고 가정하되, 사용자가 알려주지 않은 값비싼 재료는 임의로 추가하지 않도록 프롬프트에 명시한다.
- **출력**
  - 요리 이름, 예상 조리 시간, 필요 재료 목록, 조리 순서를 카드 형태로 화면에 표시한다.
- **사용자에게 제공하는 가치**
  - "뭘 해먹을지 고민하는 시간"과 "레시피를 따로 검색하는 시간"을 한 번의 입력으로 없애서, 장보기나 배달 주문으로 넘어가기 전에 있는 재료로 바로 요리를 선택하게 만든다.

### 실패 처리 기준

| 상황 | 처리 방식 | 사용자 안내 문구 |
|---|---|---|
| 빈 입력 (재료 누락) | 프론트에서 우선 검증, 서버도 동일 검증(2중 방어) | "냉장고에 재료를 넣거나, 오늘 있는 재료를 1개 이상 입력해주세요." |
| API 오류 (4xx/5xx) | 서버가 OpenAI 응답 상태를 그대로 노출하지 않고, 원인별로 502/504로 매핑 | "AI 서비스에 일시적인 문제가 발생했어요. 잠시 후 다시 시도해주세요." |
| 지연/타임아웃 | 서버 15초, 클라이언트 20초로 이중 타임아웃 설정 | "AI 응답이 지연되고 있어요. 잠시 후 다시 시도해주세요." |

**기능명 2**: 주간 식단 계획 + 장보기 리스트 (장벽 2·3 해소)

- **입력**
  - 냉장고 목록 (`pantry.html`에서 등록한 `localStorage` 재료를 그대로 읽어옴, 화면에 읽기 전용으로 표시)
  - 계획할 일수 (3/5/7일, 기본값 5일), 한 끼당 만들 분량, 건강 관리 여부 (레시피 추천과 동일한 선택지 재사용)
- **처리**
  - 서버(`api/mealplan.py`)가 재료함 목록을 프롬프트에 포함해 "이 재료를 최대한 활용하되 부족하면 새로 사도 되는" 조건으로 날짜별 아침·점심·저녁 메뉴를 JSON으로 요청한다. 끼니마다 성격을 따로 지시한다 - 아침은 5분·재료 3개 이내, 점심은 전날 저녁 활용 가능, 저녁은 제대로 된 한 끼.
  - 장보기 리스트도 같은 응답에서 함께 받는다. 처음에는 프론트가 이름을 대조해 계산했지만, "계란 2개"가 있어도 계획에 8개가 필요하면 사야 하는 것을 이름만으로는 구분할 수 없어 **수량을 아는 서버가 정하는 방식으로 바꿨다.**
- **출력**
  - 날짜별 카드 안에 아침·점심·저녁 세 칸을 두고, 각 칸에는 **끼니와 메뉴 이름만** 표시하고, 메뉴 이름 자체를 레시피로 나가는 링크로 만든다(뒤에 작은 화살표 아이콘). 재료는 화면에 내지 않는다 — 21칸에 재료를 모두 펼치면 100줄이 넘어 정작 "이번 주 뭐 먹지"가 읽히지 않는다. 무엇을 사야 하는지는 장보기 화면이, 어떻게 만드는지는 레시피 링크가 이미 답한다. (재료 데이터 자체는 유지한다. 장보기를 다시 뽑을 때 서버로 보낸다.)
  - 링크를 "만개의레시피에서 찾아보기 →" 문장으로 두지 않는 이유: 21칸에 반복되면 링크 문구가 메뉴 이름보다 길어져 화면을 뒤덮는다. 반복 자체가 의미를 알려주므로 아이콘으로 충분하고, 링크 텍스트가 요리 이름이 되어 스크린리더에도 더 정확해진다. 아이콘은 이모지가 아니라 인라인 SVG다 — 이모지는 기기마다 모양이 달라 정렬이 흔들리고, 이 서비스는 이미 이모지 사용 자리를 정리해야 할 상태다(체크리스트 10번).
  - **레시피 추천 화면은 문장을 그대로 둔다.** 카드가 1~3장뿐이라 반복이 없고, 그 링크가 화면의 결론이기 때문이다([B5](#)). 같은 요소라도 반복 횟수가 다르면 처리도 달라야 한다.
  - **짜진 식단은 사용자가 고칠 수 있다.** 다만 조작 요소를 상시 노출하지 않는다 — 21칸마다 버튼을 두면 읽는 화면을 편집 UI가 덮는다([C2](#), [C10](#)). 우측 상단 **"메뉴 바꾸기"로 편집 모드에 들어갔을 때만** 고르기·놓기·삭제가 나타난다.
  - 옮기는 방식은 **"고르고 → 놓기"**다. 메뉴를 누르면 선택되고, 옮길 자리를 누르면 이동한다. 드래그를 쓰지 않은 이유는 세 가지다. HTML5 드래그는 모바일 터치에서 동작하지 않아 별도 구현이 필요하고, 드래그만 있으면 키보드 사용자는 편집이 불가능하며([A7](#a7-구조와-표현의-일관성)), 21칸은 화면보다 길어 드래그가 세로 스크롤과 부딪힌다. 고르고 놓기는 마우스·터치·키보드가 **모두 같은 경로**로 동작한다.
  - 이미 메뉴가 있는 자리에 놓으면 **서로 자리를 맞바꾼다** — 덮어쓰면 의도하지 않은 삭제가 되고 되돌릴 방법도 없다. 메뉴를 다 지운 날짜 칸도 화면에 남겨둔다. 칸이 사라지면 거기로 다시 옮길 수가 없다.
  - 지금 무엇을 해야 하는지는 `role="status"` 한 줄로 알린다("옮길 메뉴를 누르세요" → "어디로 옮길까요?").
  - 고친 뒤에는 장보기 목록이 계획과 어긋나므로, 장보기 화면이 그 사실을 먼저 말하고 "다시 뽑기"를 권한다. 리스트 각 항목에는 쿠팡 검색 결과로 이동하는 링크(`coupang.com/np/search?q=<재료명>`)를 새 탭으로 연다.
  - **장바구니 자동 담기는 제공하지 않는다** — 쿠팡은 개인이 프로그램으로 장바구니에 상품을 담을 수 있는 공식 API가 없고, 가능한 방법(로그인 세션 자동화)은 이용약관 위반 소지와 실제 결제로 이어질 수 있는 자동화라는 위험이 있어 검색 링크 제공까지로 범위를 제한했다.
- **사용자에게 제공하는 가치**
  - "이번 주에 뭘 사야 하지"라는 계획 자체를 없애고, 이미 가진 재료는 다시 사지 않도록 걸러줘서 장보기 실수(중복 구매·누락)를 줄인다.
- **실패 처리**: 레시피 추천과 동일하게 API 오류/타임아웃에 안내 메시지를 표시한다. 재료함이 비어 있어도 AI가 처음부터 식단을 제안하므로 별도의 "빈 입력" 실패 케이스는 없다. 다만 이때는 뺄 것이 없어 식단의 모든 재료가 장보기 리스트에 담긴다(가진 게 없으면 다 사야 하니 결과 자체는 옳다). 제출을 막지 않는 이유는 첫 방문자가 정확히 이 상태로 들어오기 때문이다 — 막으면 서비스를 아예 써볼 수 없다.

## 4. 보너스 과제 — 사용자 경험(UX) 고도화

**다크 모드 지원 (구현 완료)**

- 이전에 직접 만든 냉장고 재고 관리 아티팩트(React 버전)에서 다크 모드가 실사용성이 높다고 판단해, 이번 미션에서도 같은 아이디어를 바닐라 JS로 재구현했습니다.
- 토글 클릭 시 `localStorage`에 선택을 저장해 재방문 시에도 유지되며, 최초 방문 시에는 OS의 `prefers-color-scheme` 설정을 따라갑니다.
- 효과 확인 방법: 토글을 눌러 즉시 배경/텍스트 대비가 바뀌는지 육안으로 확인할 수 있고, 개발자 도구에서 `localStorage.getItem("fridge-chef-theme")` 값으로 저장 여부를 검증할 수 있습니다.

**내 재료함 — 데이터 저장 고도화 (구현 완료)**

- 실제로 본인이 반복 사용할 서비스로 만들고 싶다는 목표에서 추가한 기능입니다. 매번 "계란, 대파, 두부"처럼 같은 재료를 반복 입력하는 게 번거롭다는 문제를 해결합니다.
- 자주 쓰는 재료는 "내 재료함"에 한 번만 등록하면 `localStorage`에 저장되어 다음 방문에도 유지되고, 그날그날 추가로 있는 재료만 별도 입력란에 적으면 됩니다. 두 입력을 합쳐서 AI에게 전달합니다.
- 서버로 전송·저장되지 않고 브라우저에만 남으므로 별도 백엔드나 로그인 없이도 "내 것"처럼 쓸 수 있습니다. (홈 FAQ에 저장 범위를 명시)

**오늘 상황 선택 + 최근 추천 이력 (구현 완료 — 팀원 프로젝트 리뷰에서 착안)**

- 팀원이 공유해준 "CareMeal" 프로젝트(나이대별 페르소나로 AI 말투를 바꾸는 방식)를 리뷰하면서, fridge-chef에도 상황에 따라 추천 스타일을 바꾸면 좋겠다고 판단해 "오늘 상황"(자취생 간단요리/가족 식사/다이어트·건강식) 선택지를 추가했습니다. 선택값은 백엔드 프롬프트에 반영되어 AI가 상황에 맞는 요리를 추천합니다.
- **이후 축소함** — 실제로 써보면서 이 선택지가 타겟과 어긋난다는 걸 발견했습니다. 상세는 아래 "타겟 정합성 점검" 참고. CareMeal에서 착안한 "상황에 따라 추천 성격을 바꾼다"는 아이디어 자체는 건강 여부 축으로 남아 있습니다.
- CareMeal의 식단 기록(히스토리) 개념에서 착안해, 최근 추천받은 요리를 최대 5개까지 `localStorage`에 저장하는 "최근 추천 이력"도 추가했습니다. 이력 항목을 클릭하면 API를 다시 호출하지 않고 저장된 데이터로 바로 카드가 다시 표시됩니다.
- CareMeal과 달리 로그인·서버 DB 없이 브라우저 로컬 저장만으로 구현해, 계정 없는 이 서비스의 구조를 그대로 유지했습니다.

**주간 식단 계획 + 장보기 리스트 — 장벽 2·3 해소 (구현 완료)**

- 처음에는 미션 범위를 넘어선다고 보고 "향후 확장 아이디어"로만 남겨뒀으나, 실제로 자주 쓸 서비스로 만들고 싶다는 목표에 비춰볼 때 장벽 2·3을 그대로 두면 서비스 가치가 절반만 실현된다고 판단해 실제로 구현했다. 상세 설계는 [3. AI 기능 설계 — 기능명 2](#3-ai-기능-설계) 참고.
- 재료함(내 재료함)을 그대로 재사용해 별도 입력 없이 식단 계획에 반영되고, 장보기 리스트는 실제 구매로 이어지는 마지막 단계(쿠팡 검색)까지 링크로 연결했다.

**UX 마찰 개선 (구현 완료 — 실사용 관점 자체 점검에서 발견)**

기능을 다 붙인 뒤 실제로 처음부터 써보면서 발견한 불편함 4가지를 고쳤습니다.

- **재료함 다중 입력**: 재료를 하나씩 입력→Enter를 반복해야 했던 것을, "오늘 추가 재료" 칸처럼 쉼표로 여러 개를 한 번에 추가할 수 있게 바꿨다.
- **mealplan.html에서 재료함 직접 수정**: 식단 계획 페이지에서 재료함이 읽기 전용이라 잘못됐을 때 recipe.html로 다시 가야 했던 문제를, 재료함 로직을 `js/shared.js`로 분리해 두 페이지 모두 완전히 같은 추가/삭제 UI를 갖도록 바꿨다.
- **선택값 기억**: 만들 분량·건강 관리 여부를 매 방문마다 다시 고르던 것을, `localStorage`(`fridge-chef-prefs`)에 저장해 recipe.html과 mealplan.html이 같은 값을 공유하도록 했다. 조리시간(레시피 전용)·일수(식단 전용)는 각 페이지에서만 기억한다.
- **삭제 확인창**: "전체 지우기"(추천 이력)·"계획 지우기"(식단)를 실수로 눌러도 되돌릴 수 없었던 것을, `confirm()` 확인 절차를 거치도록 추가했다.

**품질 점검 — 실제 동작 검증에서 발견한 결함 수정 (구현 완료)**

기능을 다 붙인 뒤 코드를 처음부터 다시 읽고 브라우저에서 직접 검증하면서, 눈으로는 잘 보이지만
실제로는 틀린 동작 4가지를 찾아 고쳤습니다. 기능 추가가 아니라 "이미 있다고 믿었던 기능이
정말 그렇게 도는지" 확인하는 작업이었습니다.

| 발견한 결함 | 실제 증상 | 조치 |
|---|---|---|
| 추천 이력의 화면 순서와 내부 배열 순서가 갈라짐 | 새로 추천받은 직후 이력을 누르면 **다른 요리가 열림** | 배열을 단일 출처로 통합 |
| 장보기 리스트의 재료 이름 비교가 한 방향 | 재료함에 "파"가 있으면 **파프리카·파스타까지 안 사게 됨** | 정규화 후 양방향 비교, 1글자 겹침은 불인정 |
| 백엔드가 AI 응답의 타입을 검증하지 않음 | AI가 예상 밖 구조를 주면 **에러 메시지도 없이 화면이 멈춤** | 서버에서 스키마 강제 |
| 다크 모드 버튼이 헤더 정중앙에 배치됨 | 로고와 메뉴 사이에 떠 있어 어색함 | flex 배치 수정 |

**진입 동선·안내 문구 보완 (구현 완료 — 배포 전 사용 흐름 점검에서 발견)**

배포 직전에 처음 방문한 사용자의 시선으로 전체 흐름을 따라가 보면서, 기능이 아니라 **동선과 문구**에서
비어 있는 두 곳을 찾아 고쳤습니다.

| 발견한 문제 | 실제 증상 | 조치 |
|---|---|---|
| 홈이 레시피 추천만 소개함 | 장벽 2·3을 해소하는 주간 식단이 네비게이션 링크로만 존재해, 첫 방문자가 **서비스 가치의 절반을 발견하지 못함** | 히어로에 보조 CTA 추가, 기능 카드 3번째를 주간 식단으로 교체 |
| 재료함이 빈 채로 식단을 만들면 | 모든 재료가 리스트에 담기는데 안내는 "재료함에 없는 재료만 모았어요"라고 표시 — **걸러낸 적 없는데 걸러낸 것처럼 보임** | 재료함 유무로 문구 분기, 재료함 섹션 설명에도 기대치 명시 |

**UI/UX 원칙 기반 개선 (구현 완료 — 원칙 문서를 만들고 그 기준으로 전 화면 검토)**

[UI/UX 원칙](./UIUX원칙.md)을 안전·배려·디자인 3축으로 정리하면서 현재 화면을 그 기준으로
검토했고, 어긋난 항목 중 결함 4건과 체감이 큰 6건, 그리고 신규 기능 1건을 처리했습니다.

| 발견한 문제 | 실제 증상 | 조치 |
|---|---|---|
| 재료함 조작에 반응이 없음 | 이미 있는 재료를 다시 추가하면 화면이 그대로라 **고장으로 보임** | 다섯 경우 모두 상태 문구 표시 |
| 추천 카드가 재료를 나열만 함 | 주간 식단은 재료함과 대조하는데 레시피 추천은 안 해서, **뭐가 내 것인지 직접 기억**해야 함 | 같은 판정으로 보유/미보유 표시 |
| 추천이 마음에 안 들면 | 폼까지 되돌아가 다시 제출해야 함 | "다른 요리 추천받기" 버튼 |
| 실패하면 갈 곳이 없음 | "잠시 후 다시 시도"로 끝남 | 이력이 있으면 그쪽으로 안내 |
| 주 행동이 화면 한가운데 | 재료함이 폼보다 위에 크게 있어 **처음 온 사람이 뭘 할지 모름** | 재료함을 `<details>`로 접고, "추가" 버튼을 강등해 주황 채움을 제출 버튼 하나로 |
| 조리 순서가 3~5줄로 얕음 | 카드에서 흐름이 끝나 실제 요리로 이어지지 않음 | **만개의레시피 검색 링크** 추가 |
| 모바일 관례 위반 | 삭제 버튼 터치 타겟 20px, 제출 버튼이 좁게 왼쪽 정렬 | 히트 영역 44px, full-width |
| 다크 모드에서 오류 상자 | 테두리만 하드코딩 색이라 테마를 벗어남 | 토큰화 |

**만개의레시피 연결의 설계 판단**: 검색어로 요리 이름을 그대로 넘기면 안 됩니다. 만개의레시피는
긴 검색어를 단어별로 느슨하게 매칭해서, "냉장고털이 두부 계란 덮밥"으로 검색하면 결과가 0건이
아니라 **3만 건의 무관한 레시피**가 나옵니다(실측). 그래서 AI에게 검색용 짧은 이름을 따로 받고,
없으면 요리 이름으로 대체합니다. 쿠팡 링크와 마찬가지로 **검색 결과까지만** 보내고 그 이상은
하지 않습니다.

**타겟 정합성 점검 (구현 완료 — 실사용 중 발견한 모순)**

기능을 다 붙이고 직접 써보다가, **기획서가 정의한 타겟과 화면이 묻는 질문이 어긋난다**는 걸
발견했습니다. 1장에서 타겟을 "20대 1인 가구 자취생"으로 못박아 놓고, 정작 폼은 "가족 식사"와
"3~4인분"을 묻고 있었습니다. 혼자 사는 사람만 쓰는 서비스가 *"당신은 자취생입니까?"* 를
매번 묻고 있던 셈입니다.

"오늘 상황" 4지선다를 하나씩 따져보니 3개가 문제였습니다.

| 선택지 | 판단 | 조치 |
|---|---|---|
| 기본 | 아래가 기본값이 되면 중복 | 제거 |
| 자취생 간단요리 | 전원이 자취생이면 **선택지가 아니라 기본값** | 시스템 프롬프트로 승격 |
| 가족 식사 | 타겟과 정면 모순 | 제거 |
| 다이어트/건강식 | 세대 구성과 무관한 유효한 축 | 체크박스 하나로 남김 |

**"인원수"는 기능이 아니라 이름이 틀린 경우였습니다.** 자취생도 2인분을 만듭니다 — 내일
점심으로 남기려고요. 오히려 이게 이 기획이 말하는 식비 절약의 핵심 행동입니다. 같은 값인데
`3~4인분`은 타겟에게 안 맞고 `3~4끼 분량`은 정확히 맞으므로, 선택지를 타겟의 언어로 바꿨습니다.

| 이전 | 현재 |
|---|---|
| 인원수: 1인분 / 2인분 / 3~4인분 | 만들 분량: 한 끼 / 두 끼(내일 점심까지) / 3~4끼(며칠치) |

이 점검으로 폼 필드가 하나 줄고, 남은 선택지는 전부 타겟에게 의미가 생겼습니다.
"기능을 더하는 것"이 아니라 **"타겟에 맞지 않는 것을 걷어내는 것"** 도 개선이라는 사례입니다.

**페이지 통합 (구현 완료 — 카테고리를 줄여 인지 부하 낮추기)**

페이지가 4개에서 3개로, 네비게이션 항목도 4개에서 3개로 줄었습니다. 소개 페이지를 홈에 합쳤습니다.

다만 **그냥 이어 붙이지는 않았습니다.** 두 페이지에 3개짜리 설명 블록이 하나씩 있었고 내용이
거의 같았기 때문입니다. 그대로 붙이면 홈에 비슷한 블록이 연달아 나와 인지 부하가 오히려 늘어납니다.

| 홈 `features` | 소개 `이용 방법` |
|---|---|
| 재료만 입력하세요 | ① 재료 입력 |
| 레시피까지 한 번에 | ② AI 추천 요청 |
| 이번 주 장보기까지 | ③ 레시피 확인 |

그래서 하나로 합쳤습니다. 순서가 있는 3단계이므로 이모지 아이콘 대신 번호를 쓰고, 각 단계에
실제로 얻는 것(재료함 자동 반영, "사야 해요" 표시, 만개의레시피 링크, 재추천)을 적었습니다.
주간 식단은 단계에 억지로 끼워넣지 않고 3단계 아래 "다음 행동"으로 안내합니다.

**기술 스택은 지우지 않고 FAQ 항목("어떤 기술로 만들었나요?")으로 접어 넣었습니다.** 저녁 메뉴를
정하러 온 사람에게 필요한 정보는 아니지만, 궁금한 사람은 펼쳐 볼 수 있어야 하기 때문입니다.

이 통합으로 함께 해소된 것: 소개 3단계 끝에 "지금 해보기" 버튼이 없던 문제(홈이므로 히어로 CTA가
그 역할), 소개 이용 방법에 주간 식단이 빠져 있던 문제, "냉털" 뜻풀이가 소개에만 있던 문제.

**책임 단위 재편 — 냉장고를 독립 화면으로 (구현 완료)**

이 서비스의 핵심 자산은 냉장고인데 전용 화면이 없었습니다. 재료함 편집 UI가 레시피 추천과
식단 계획 양쪽에 박혀 있어, 두 페이지 모두 **한 화면에서 여러 일**을 하고 있었습니다.

| 파일 | 재편 전 책임 | 재편 후 |
|---|---|---|
| `recipe.html` | ① 재료함 관리 ② 추천받기 ③ 이력 보기 | 추천받기 (+이력) |
| `mealplan.html` | ① 재료함 관리 ② 식단 계획 ③ 장보기 리스트 | 식단 계획 |
| — | | `pantry.html` 냉장고 (신규) |
| — | | `shopping.html` 장보기 (신규) |

**직전의 "소개 → 홈 통합"과 모순되지 않습니다.** 그때는 *중복 제거*(같은 말을 두 번 하던 것)였고,
이번은 *책임 분리*(한 화면이 여러 일을 하던 것)입니다. "필요한 만큼만"은 **최소로 만들라는 뜻이 아닙니다.**

부수 효과로 네비 이름이 선명해졌습니다 — "주간 식단"은 이름만 봐선 장보기를 품고 있는 줄 몰랐는데,
이제 "식단 계획"과 "장보기"가 각각 있습니다.

**세 화면 공통의 냉장고 조회 바**: 레시피 추천·식단 계획·장보기는 모두 "지금 냉장고에 뭐가 있는지"를
알아야 판단이 됩니다. 헤더 아래 접이식 바를 상시 배치하되 **조회 전용**으로 두어, 편집은 냉장고
한 곳에 모았습니다. 사이드바가 아니라 전체 폭 바로 만든 이유는 단일 컬럼을 유지해야 본문 왼쪽 끝이
헤더 로고와 계속 맞기 때문입니다(과거에 실제로 어긋나서 고쳤던 문제).

**장보기 → 냉장고 고리**: 각 항목의 "샀어요"를 누르면 냉장고에 들어가고 리스트에서 사라집니다.
`냉장고 → 식단 → 장보기 → 냉장고`로 흐름이 닫힙니다. 화면에는 원문(`김치 200g`)을 보여주지만
냉장고에는 정규화된 이름(`김치`)을 넣습니다 — 수량이 붙은 채로 들어가면 다음 계산에서 매칭이 어긋납니다.

**빈 상태 4종을 함께 채웠습니다.** 페이지를 나누면 빈 화면이 늘어나므로, 각 화면에 "여기서 뭘 하면
되는지"를 넣지 않으면 분리 전보다 나빠집니다. 특히 냉장고의 빈 상태에는 **눌러서 바로 넣는 예시 칩**을
두어, 첫 방문자가 빈 입력란 앞에서 멈추지 않게 했습니다.

**이번 재편에서 생긴 회귀 하나**: 네비 항목이 4개에서 5개로 늘면서 모바일 메뉴의 `max-height: 240px`을
링크 총높이(274px)가 넘어 마지막 항목 "장보기"가 잘렸습니다. 브라우저에서 직접 재보고 찾아 고쳤습니다.

**접근성 개선 (구현 완료)**

마우스 없이 키보드만 쓰거나 화면을 보지 못하는 사용자도 "재료 입력 → 추천 확인"이라는 핵심 흐름을
끝까지 갈 수 있는지를 기준으로 점검했습니다. 본문 바로가기 링크, AI 진행·결과의 `aria-live` 안내,
닫힌 모바일 메뉴가 키보드 포커스를 가져가지 않도록 하는 처리, Esc·바깥 클릭으로 메뉴 닫기,
초점 표시(`:focus-visible`), 모션 최소화 설정(`prefers-reduced-motion`) 존중을 추가했습니다.
상세 근거는 [README 설계 노트](../README.md#-설계-노트), 이 결정들이 공유하는 판단 기준은
[UI/UX 원칙](./UIUX원칙.md) 참고.

### 향후 추가 확장 아이디어 (미구현)

- 재료함 항목에 유통기한을 함께 저장해, 임박한 재료를 우선 추천하도록 AI 프롬프트에 반영
- 방문자 수 간단 카운팅으로 실제 사용 데이터를 확인

### 남은 일: 60MB를 이 PC 밖으로

지금 만든 압축본은 **같은 디스크에** 있다. 실수로 지우는 것은 막아주지만 디스크가
죽으면 같이 죽는다. 하나 이상 골라 복사한다.

| 방법 | 장점 | 주의 |
|---|---|---|
| 개인 클라우드 (OneDrive·Google Drive 등) | 기기 밖, 자동 | **공유 링크를 만들지 않는다.** 비공개 유지 |
| 외장 디스크·USB | 오프라인, 계정과 무관 | 꽂아둔 걸 잊으면 같이 젖는다 |
| GitHub **비공개** 저장소 | 버전 관리 | 60MB는 되지만 100MB 한도가 가깝다. 공개 저장소는 절대 안 됨 |

> 저장소 폴더가 OneDrive 안에 있다는 것은 백업이 아니다 — 여기서 지우면 삭제도
> 같이 동기화된다. 휴지통·버전 기록이 얼마간 막아주지만 "몇 달 뒤에 알아차림"은 못 막는다.

복사한 뒤 그 사본에서 `certutil -hashfile <파일> SHA256`으로 한 번 확인한다.
옮기다 깨지는 일은 실제로 있다.

- [ ] (선택) 루트의 중복 CSV 2개 삭제로 25MB 회수 —
      `TB_RECIPE_SEARCH_241226.csv`, `TB_RECIPE_SEARCH_251231.csv`.
      백업이 기기 밖으로 나간 **뒤에** 한다

## 3. 매칭 최적화 — ✅ 완료 (2026-08-23)

**한 것**

- 역색인을 요청 프로세스마다 다시 만들지 않고 빌드 때 만들어 파일에 넣는다
  (`build_recipe_index.pack()`)
- 재료명·시간·인분·카테고리를 정수 id로 (재료명은 고유 62,150종이 217만 칸에 평균 35번 중복)
- 재료 중복을 빌드 때 제거해 채점 루프가 후보마다 `set()`을 만들지 않게 한다
- 인덱스에 포맷 버전(`"v": 2`)을 넣고, 안 맞으면 깨진 파일과 똑같이 취급해 AI 폴백
- `deploy.sh`에 빌더/인덱스 mtime 비교 추가

**측정 — 로컬 (재현됨)**

```
파일        50.6MB -> 30.6MB      -40%
콜드(로드)  1,452ms -> 544ms      2.7배
웜(재료 7)    216ms -> 127ms      1.7배
메모리       324MB -> 207MB       -36%   (Vercel 한도 1024MB)
```

추천 결과는 냉장고 5개 × 분량 3가지 = 15줄을 대조해 **최적화 전과 완전히 동일**했다.

**측정 — 프로덕션 (기대와 달랐다)**

새 배포의 첫 요청으로 깨끗하게 재보니:

```
최적화 전  4.35s
최적화 후  4.63s      -> 줄지 않았다
```

원인을 갈라 보려고 인덱스를 안 타는 경로(빈 재료 → 400)로 새 배포의 첫 요청을 재보니
**2.29초**가 나왔다. 즉 콜드의 절반은 컨테이너 기동 + 파이썬 + `openai` import이고,
우리가 줄인 인덱스 로드는 그 위에 얹히는 일부다. 게다가 Vercel 콜드는 같은 코드로도
4.2~6.9초로 흔들려서, 로컬에서 아낀 900ms가 그 편차에 묻힌다.

웜 왕복도 0.83~0.96초로 최적화 전(0.83~0.86초)과 구분되지 않는다 — 네트워크 왕복
0.35초와 Vercel CPU 편차가 로컬에서 아낀 90ms보다 크다.

> **정직하게 적어둔다.** 이 작업을 시작할 때 내세운 "콜드 4.7배"는 로컬 기준이었고,
> 프로덕션에서는 재현되지 않았다. 서버리스 콜드 스타트는 우리 코드가 아니라 플랫폼이
> 정한다. 다음에 성능 작업을 할 때는 **실제 배포 환경에서 먼저 병목을 갈라보고**
> 시작해야 한다.

**그래도 남기는 이유**

- 파일 20MB 감소는 실제 이득이다 — 함수 번들 상한 225MB에 여유가 늘고 업로드가 빨라진다
- 메모리 117MB 감소도 실제 이득이다 — 코퍼스가 커질 때 먼저 닿을 벽에서 멀어진다
- 포맷 버전과 mtime 검사는 성능과 무관하게 **1번 같은 사고를 막는 장치**다
- 결과가 완전히 동일하고 테스트가 늘었으므로(54개), 되돌릴 이유가 없다

**남은 것**

- [x] 매칭 카드의 재료 수량 (2026-08-23) — 바로 이어서 했다. 인덱스가 커지는 게

## 안 하기로 한 것

- **폰트 292KB 줄이기.** 전송량 656KB 중 617KB가 웹폰트고 그중 `MaruBuri-Bold.woff2`가
  292KB다(h1·`.brand`에만 쓰는데 한글 전체 글리프를 받는다). 줄이려면 서브셋 폰트를
  만들어 자체 호스팅해야 하는데 `fonttools` 실행이 필요하다 — 이 프로젝트의
  "빌드 스텝 없음" 원칙과 부딪힌다. 성능이 아니라 판단의 문제라 따로 정한다.
- **프론트 코드 최적화.** 자체 CSS+JS는 gzip 후 40KB 남짓이고 `loadPantry()`도
  렌더당 한 번씩만 부른다. 짜낼 게 없다.
- **`js/test_amounts.js`가 프로덕션에 배포되는 것**(`GET /js/test_amounts.js` → 200).
  `vercel.json`의 `js/**` 글롭 때문이다. 사용자 대역폭은 안 쓰지만 테스트 코드가
  공개된다. 급하지 않아 뒤로 미룬다.
